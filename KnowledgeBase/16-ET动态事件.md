## 模块定位

DynamicEvent 是按参数类型、SceneType 和实体精确类型，对 Main Scene 内已注册 ET Entity 做进程内广播的扩展。它支持 fire-and-forget 与等待全部处理器，不跨 Fiber、进程或网络，也不替代 Actor 消息/RPC。当前仓库静态检索未发现模块外 `ADynamicEvent<TEntity,TArg>` 业务实现、`DynamicEventReceiverComponent` 添加点或业务侧 `DynamicEventComponent.Publish/PublishAsync` 调用；本文的处理器代码块是接入写法示例，接入后仍需运行时验证。

## 依赖关系

- 依赖 ET Entity/EntityRef、CodeTypes、SceneType、TimeInfo、ListComponent 和 UniTask。
- `EntryEvent1_InitDynamicEvent` 只响应 `SceneType.Main`，注册表属于 Main Scene/Fiber。
- 处理器由带 `[Code]` 的 Singleton 在当前 CodeTypes 中扫描 `[DynamicEvent]` 类型。
- reload 入口来自 `CodeLoaderComponent.ReloadAsync()`，实际由 `CodeLoader.ReloadAsync()` 重新加载 Hotfix/HotfixView、注册新的 `CodeTypes`，再执行 `CodeTypes.CreateCode()`；因此 `DynamicEventTypeSystem` 会作为 `[Code]` Singleton 被重建。
- 参数必须是 struct；接收者必须挂 `DynamicEventReceiverComponent`。
- UGF Event、ET 普通 EventSystem 和 DynamicEvent 是不同分发机制。

## 入口与调用链

类型目录：`ET.Entry.StartAsync` 先调 `CodeTypes.CreateCode()`；`DynamicEventTypeSystem` 作为 `[Code]` Singleton 从当前 `CodeTypes` 扫描并实例化所有 `[DynamicEvent]` 处理器。

初始化：随后 Entry 创建 Main Fiber；`FiberInit_Main` 发布 EntryEvent1 -> Main 处理器给 Main Scene 添加 `DynamicEventComponent`。

注册：这是业务接入后的链路。实体添加 Receiver -> Awake 从 `Root()` 取得 DynamicEventComponent -> 以 `entity.GetType()` 加入列表；Destroy 只加入待移除列表，下一次 Update 删除。当前仓库未发现模块外给实体添加 Receiver 的调用点。

发布：按参数运行时 Type 找处理器 -> `HasSameFlag` 过滤 SceneType -> 按处理器 EntityType 精确查实体列表 -> 对有效 EntityRef 调 `Handle`。同步版对每个任务 `.Forget()`；Async 版收集后 `UniTask.WhenAll`。当前仓库的外部 `.Publish/.PublishAsync` 命中均为 `EventSystem.Instance`，未发现业务侧调用 `DynamicEventComponent.Publish/PublishAsync`。

热重载：Console `ReloadDllConsoleHandler` 或 Editor `CompileDllToolBar_ET` 最终调用 `CodeLoaderComponent.ReloadAsync()` -> `CodeLoader.ReloadAsync()` -> `CodeTypes.CreateCode()`；这会重建 `[Code]` Singleton，包括 `DynamicEventTypeSystem`，但不会重跑 EntryEvent1，也不会自动给业务实体补 Receiver。

## 核心类型与 API

| 类型/API | 职责 | 生命周期/线程约束 |
| --- | --- | --- |
| `ADynamicEvent<A,B>` | A 为实体，B 为 struct 参数 | `Run(A,B)` 返回 UniTask；Handle 捕获异常 |
| `[DynamicEvent(SceneType)]` | 声明处理器作用域 | 默认 All；允许同类多次标注 |
| `DynamicEventTypeSystem` | `[Code]` Singleton，缓存 ArgType -> handler 列表 | 初次 Entry 和 reload 的 `CodeTypes.CreateCode()` 都会重建 |
| `DynamicEventReceiverComponent` | 自动注册/反注册 Parent | Root 必须有 DynamicEventComponent |
| `Publish(arg)` | 使用组件所属 SceneType，不等待 | 处理器任务 fire-and-forget |
| `Publish(sceneType,arg)` | 显式指定过滤 SceneType | 仍使用同一个 Main 注册表 |
| `PublishAsync*` | 并发等待全部匹配处理器 | 不保证顺序或业务成功 |

## 数据与生命周期

- 注册表是 `Dictionary<Type,List<EntityRef<Entity>>>`，键为实体精确运行时类型。
- 反注册延迟到下一帧 Update；失效 EntityRef 不会被执行。
- 每 60 秒全量移除失效引用，发布时也顺便清理当前匹配列表。
- `ADynamicEvent.Handle` 捕获并记录每个处理器异常，因此 `PublishAsync` 不向调用者传播业务失败。
- 热重载的实际链路是 `CodeLoader.ReloadAsync` 重新加载 Hotfix/HotfixView -> 注册新 `CodeTypes` -> `CodeTypes.CreateCode()` 重建 `[Code]` Singleton；可发现新处理器，但不会重跑 EntryEvent1，也不会自动创建 Receiver。
- Scene 上已有 `DynamicEventComponent` 和已注册实体列表属于运行中 Entity 状态，不随 Hotfix/HotfixView 程序集重载自动丢失；如果业务实体从未挂 Receiver，reload 也不会让它们开始接收动态事件。

## 开发扩展步骤

1. 定义唯一的 readonly struct 参数。
2. 实现 `ADynamicEvent<TEntity,TArg>`，添加 `[DynamicEvent(SceneType.X)]`，在 `Run` 中返回 UniTask。
3. 给 Main Fiber 中的目标实体添加 `DynamicEventReceiverComponent`。
4. 从 `scene.Root().GetComponent<DynamicEventComponent>()` 调 Publish 或 PublishAsync。
5. 有顺序、结果、跨 Fiber 或网络要求时，改用显式服务/Actor 请求，不要叠加 DynamicEvent。

下面代码只说明当前 API 的最小写法；当前仓库未发现同类业务处理器、Receiver 添加点或 Publish 调用，不能据此认为业务已经接入或运行通过。

```csharp
[DynamicEvent(SceneType.Client)]
public sealed class RefreshLevel : ADynamicEvent<Player, PlayerLevelChanged>
{
    protected override UniTask Run(Player self, PlayerLevelChanged arg)
    {
        self.Level = arg.Level;
        return UniTask.CompletedTask;
    }
}
```

## 约束与常见错误

- 旧示例的 void `Handle` 覆写不存在；当前必须覆写 `protected UniTask Run(A self, B arg)`。
- 基类处理器不会自动接收派生实体，注册与查询都是精确 Type。
- Receiver 的 `Root()` 没有 DynamicEventComponent 时 Awake 会空引用；其他 Fiber 默认未初始化本模块。
- Async 处理器并发执行且异常被内部吞并记录，不能提供事务、顺序或成功结果。
- 适合低频状态通知；每帧向大量实体广播会线性扫描并产生 UniTask 调度成本。
- 显式传 SceneType 只改变过滤条件，不会跨到该 SceneType 所在的其他 Fiber。
- 当前仓库静态检索只证明模块具备框架能力；没有模块外处理器、Receiver 添加点或业务 Publish 调用时，不能把本文示例写成真实业务已接入。
- reload 只刷新处理器类型系统；Receiver 列表、实体生命周期和业务发布点仍由运行中 Scene/Entity 决定。
