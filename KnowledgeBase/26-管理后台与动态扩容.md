## 模块定位

本模块覆盖两类状态不同的能力：

- **已实现的运维控制面**：Admin 是运行在 `AppType.Admin` 进程内的 ASP.NET Core Blazor Server + MudBlazor 应用，借助 ET Actor RPC 查询服务器并经 Agent 执行进程启停、文件部署协议和热重载。
- **尚未实现的弹性扩容**：当前运行拓扑仍由 Luban 的 Machine、Process、Scene、Zone 静态表决定。`Book/动态扩容.md` 中的 Registry、租约、Route Snapshot、Draining、Gate 一致性哈希、Map 伸缩和 Location 分片均是设计目标，不是仓库现成功能。

`verified` 表示本文已按源码和配置做静态核验；不表示 Admin/Agent 已在隔离环境运行，也不表示动态扩容已实现或通过生产安全验收。

## 依赖关系

- `DotNet/Hotfix/DotNet.Hotfix.csproj` 使用 `Microsoft.NET.Sdk.Razor`、`net8.0` 和 `Microsoft.AspNetCore.App`，默认编译 `DotNet/Hotfix/Server/Admin`、`Agent`，并链接 Unity 目录下的 ET Server Hotfix 源码。
- `DotNet.Hotfix` 引用 `DotNet.Loader` 和 `DotNet.Model`；后者继续依赖 `DotNet.ThirdParty`。关键 NuGet 版本为 LiteDB 5.0.21、MudBlazor 7.15.0、UniTask 2.5.10、MemoryPack 1.10.0。
- Admin 的 Web 服务与 ET Fiber 同进程运行。`ActorRpcBridge` 把 ASP.NET Core 服务调用投递回 Admin Fiber 的 `ThreadSynchronizationContext`，再由 `MessageSender` 发送 Actor RPC。
- Admin 和 Agent 都依赖完全一致的 Luban `DTStartProcessConfig`、`DTStartSceneConfig`。进程到 Agent、Scene、IP/Port 的选择不是运行时服务发现。
- `AdminMessage.proto` 没有身份、角色、签名或授权字段；Agent Handler 也没有消息来源/角色检查。因此 ET 内网隔离和可信调用方是当前安全前提，不能把 Web Cookie 登录等同于 Agent 消息级认证。

## 入口与调用链

### 启动与认证

1. `dotnet App.dll --AppType=Admin --Process=<id> --StartConfig=<name>` 启动服务端。
2. `EntryEvent2_InitServer` 从静态 Process/Scene 表创建 NetInner 与 Admin Scene Fiber。
3. `FiberInit_Admin` 安装 MailBox、Timer、ProcessInnerSender、MessageSender 和 `ActorRpcBridge`，然后创建 `AdminComponent`。
4. `AdminComponent.StartAsync()` 注册 Razor Components、MudBlazor、Cookie 认证、授权、控制器、健康检查和后台监控，并非阻塞启动 Kestrel。
5. 登录页通过 `wwwroot/js/auth.js` POST `/api/auth/login`；`AuthService` 从 LiteDB 查询用户，以 PBKDF2-SHA256（120,000 次、随机 16 字节 salt、32 字节 hash）校验密码，成功后由 `AuthController` 签发 8 小时可滑动 Cookie。
6. `Routes.razor` 对登录页之外的 Razor 路由使用 `AuthorizeView`；`AdminAuthStateProvider` 从请求 Cookie 恢复 Blazor circuit 的认证状态。

### 进程控制、部署与热重载

1. Server 页面调用 `ProcessManagerService`，后者按 Process 的 Machine 从静态 Scene 表查 Agent。
2. `AgentActorService` 组装 `Admin2Agent_*` 请求，经 `ActorRpcBridge -> MessageSender -> NetInner` 到目标 Agent Fiber。
3. 启动由 `Admin2Agent_StartProcessHandler` 调用 `WatcherHelper.StartProcess(processId)`；Agent 仅在内存 `AgentProcessComponent.Processes` 中跟踪本次启动的子进程。
4. 停止只接受该字典内的进程，调用 `Kill(entireProcessTree: true)` 并最多等待 5 秒；这是强制终止，不包含 Draining、会话迁移或优雅停机。
5. 部署协议有两条写入路径：不超过 1 MiB 的文件直接 `File.WriteAllBytesAsync(targetPath, ...)`，大文件才分块写入 `.tmp` 并最终 `File.Move(..., overwrite: true)`。`ResolveTargetPath` 只把词法路径限制在 `AppContext.BaseDirectory` 内；当前仓库只有 `AgentActorService.DeployFileAsync` 与 Handler，未找到 Admin 页面/服务调用者，不能声称 UI 部署流程已接通。
6. 热重载由 `HotReloadService` 按 Agent 分组进程，Agent 再向各进程 Main Fiber 发送 `Admin2S_ReloadRequest`；目标 Handler 分别调用 `ConfigComponent.ReloadAllAsync()`、`CodeLoaderComponent.ReloadAsync()` 或两者。

### 当前静态拓扑

`Share/Aspire/Program.cs` 遍历 `DTStartProcessConfig` 且把 `replicasNum` 固定为 1。`ProcessOuterSenderSystem` 直接使用 `ActorId.Process` 查询静态 IPEndPoint 并缓存 Session。仅增加 Aspire 副本数会复用 ProcessId、SceneId 和端口，产生监听、Actor 身份及路由冲突。

## 核心类型与 API

| 类型/API | 职责 | 生命周期/线程约束 |
| --- | --- | --- |
| `FiberInit_Admin` | 建立 Admin Scene 组件和 Actor RPC 桥，启动 Web 服务 | Admin Fiber 初始化时执行；桥接调用回投 Fiber 同步上下文 |
| `AdminComponent.StartAsync` | 组装并启动 ASP.NET Core 应用 | 单例；源码未保存 `WebApplication` 供显式 Stop/Dispose |
| `AuthService` | Bootstrap 用户、PBKDF2 校验和 circuit 内认证状态 | Scoped，避免跨浏览器共享登录状态 |
| `AdminAuthStateProvider` | Cookie Claims 与 Blazor `AuthenticationState` 互转 | Scoped 到 Blazor circuit |
| `AdminDatabase` / `VersionService` | LiteDB 持久化用户、配置、玩家、热更与版本记录 | 单例服务；分别使用 `admin.db`、`versions.db` |
| `ActorRpcBridge` / `ActorBridgeService` | ASP.NET Core Task 与 ET UniTask/Actor RPC 的桥接 | 调用必须回到有效 Admin Fiber；超时由服务包装 |
| `ProcessManagerService` | 从静态拓扑列出并启停进程 | 单例；状态来自心跳缓存和 Agent 调用，不是进程注册中心 |
| `AgentActorService.DeployFileAsync` | 单文件或 1 MiB 分块传输 | 整个文件先以 `byte[]` 驻留 Admin 内存；当前无上层调用者 |
| `Admin2Agent_*Handler` | Agent 侧启停、写文件、转发热重载 | Agent Fiber 串行处理；具备高权限副作用 |
| `Admin2S_ReloadHandler` | 执行 code/config/all 热重载 | 目标进程 Main Scene；失败通过响应返回 |

## 数据与生命周期

- 首次启动在 `Bin/Data/admin.db` 的 `users` 为空时创建 Bootstrap 管理员；已有用户库不会被配置中的新口令覆盖。版本数据写入 `Bin/Data/versions.db`。
- Cookie Data Protection key 持久化到 `Bin/Data/DataProtectionKeys`。Windows 使用机器级 DPAPI；非 Windows 源码没有额外的静态 key 加密配置，必须依靠文件权限或外部 key 管理。
- Cookie 为 `HttpOnly`、`SameSite=Strict`，SecurePolicy 是 `SameAsRequest`。默认 Kestrel 配置为 `http://*:5200`，生产必须在可信反向代理或 Kestrel 上终止 TLS，并保护 Data、日志和配置目录。
- Agent 进程表只保存当前 Agent 启动且仍被跟踪的 `System.Diagnostics.Process`。Agent 重启后不会从 OS 重新发现旧子进程，停止请求也不会操作未跟踪进程。
- 小文件直接覆盖目标，写入中断可能留下截断文件；分块部署缺少内容 hash/签名、总长度、事务 id 和严格块序校验，并发写同一目标可能互相覆盖。
- `GetFullPath`/`GetRelativePath` 可拒绝绝对路径和 `..` 等词法逃逸，但不会解析路径组件中的 symlink、junction、mount/reparse point。若根内已有指向根外的链接、Agent 对目标可写且调用方可提交部署请求，文件 API 可能跟随链接写到根外；当前示例 NetInner 仅监听回环地址且未找到部署上层调用者，因此这是条件性风险，不是已证实的 Web/远程漏洞。
- 动态扩容若落地，必须新增 Node/Scene 实例身份、带租约 Registry、版本化 Route Snapshot、健康/Ready/Draining 状态和路由更新；当前数据模型不拥有这些生命周期。

## 开发扩展步骤

新增一个最小管理操作时：

1. 在 `Design/Proto/ET-Admin/AdminMessage.proto` 定义 Request/Response，运行仓库 Proto 生成工具，检查 `DotNet/Model/Generate/Message/Message_ET_Admin.cs`，不要手改生成物。
2. 在真正拥有副作用的 Scene（Server 或 Agent）实现 `[MessageHandler]`，先校验目标、范围、幂等性和失败回滚；高权限操作应补来源认证/授权和审计字段。
3. 在 `AdminActorService` 或 `AgentActorService` 增加有超时的桥接方法，再由 Admin Service 封装业务选择和审计记录。
4. 在受认证路由下接入页面；若角色不同，新增授权 policy/role 检查，不能只依赖“已登录”。
5. 添加 Handler、路径/参数校验、超时、重复请求和部分失败测试，并在隔离机器验证真实副作用。

动态扩容不得从复制现有 Process 配置开始；应按 `Book/动态扩容.md` 先落 Registry/租约和运行实例身份，再迁移地址解析、Scene 生命周期与业务路由，每阶段保留回退到静态拓扑的开关。

## 约束与常见错误

- **默认凭据**：仓库配置仍含 `admin/admin123`。空库首次启动前必须通过受管配置或 `Admin__BootstrapPassword` 替换；不要把密钥提交到仓库或命令行历史。
- **暴露面**：默认监听 `http://*:5200` 且 `AllowedHosts=*`。必须限制监听/防火墙、启用 TLS、设置可信代理，并决定 `/healthz` 与公开 `GET /api/version/{platform}` 的可达范围。
- **认证强度**：目前没有登录限流、锁定、MFA；有 Role claim，但未配置角色 policy，所有已认证 Razor 页面共享同一授权级别。登录和高风险操作需补审计与告警。
- **Actor 授权**：Proto 和 Agent Handler 没有调用方凭据；启动 Handler 也未验证目标 Process 是否归属本机 Agent。不要把 Agent ET 端口暴露到不可信网络。
- **部署完整性**：词法目录边界检查不等于物理路径 containment 或供应链校验。上线前需限制到服务端白名单目录，拒绝/安全解析链接与 reparse point，并验证签名/hash、大小、块序和并发事务；使用最小权限服务账户。高保障场景还需使用句柄级策略抵御检查后置换（TOCTOU）。
- **停机语义**：当前 Stop 是整棵进程树强杀，不会排空流量。维护模式只阻止 `StartServerAsync`，不是集群级流量开关。
- **状态表述**：Admin 页面和协议存在不等于端到端可用；文件部署无 UI 调用者，动态扩容完全未实现。
- **静态身份**：ProcessId、SceneId、内外端口必须唯一，所有节点配置必须一致。不要把 `replicasNum` 改大当作扩容。

## 验证方法

本次已执行静态核验：逐项读取两份 Book、Admin/Agent 源码、Admin Proto、Hotfix csproj、Aspire 编排和静态路由实现，并运行本文末所列知识库校验命令。

建议在具备 .NET 8、已还原 NuGet、有效 Luban 配置和隔离测试机时执行。构建前必须先用项目要求的 Unity 版本完成 Package 解析，并确认 `Unity/Library/PackageCache/com.unity.mathematics*` 可供 `DotNet.ThirdParty.csproj` 编译：

```powershell
dotnet build DotNet/DotNet.sln --no-restore

# 终端 A：该进程持续运行，准备就绪后再在终端 B 检查健康端点
Push-Location .\Bin
dotnet .\App.dll --AppType=Admin --Process=100002 --StartConfig=Localhost --Console=1
# 保持终端 A 运行；结束时停止进程，再执行 Pop-Location
```

终端 B：

```powershell
Invoke-WebRequest http://localhost:5200/healthz
```

随后验证：错误/正确登录、Cookie 隔离、未认证页面跳转、Fiber/Scene 查询；再以无生产数据的 Agent 验证允许和拒绝的 ProcessId、启停超时、小文件中断、分块失败恢复、hash/签名策略以及 code/config/all 部分失败。Windows 用 junction/symlink、Linux 用 symlink 将根内目录指向根外哨兵目录，覆盖小文件、分块和最终替换；请求必须 fail closed，根外内容与元数据不得变化。还要验证并发置换、未认证/篡改/重放消息均在任何写入前被拒绝并记录审计。动态扩容当前没有可执行验收项，只能验证“静态单副本约束仍成立”。
