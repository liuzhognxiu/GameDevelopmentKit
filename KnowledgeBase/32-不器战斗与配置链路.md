## 模块定位

本模块覆盖《不器》当前稳定的 Battle/Headless/Charge/配置链路。它回答“战斗内核如何保持纯 C# 确定性、approved hash 如何阻断漂移、v0.4.1 基础契约与 `buqi-effects-cv1` 内容扩展如何分层、Luban 当前扩展基线如何接入战斗定义、Unity 与 headless 局部门禁证明到哪里为止”。它不负责正式玩家 UI、完整经济、完整内容体验、服务端对战或全仓五项运行验收。

旧的 Step 3 `9 法门 / 3 淬炼 / 6 道影` 是历史门禁，用来证明 Luban 最小链路能从 Excel 导出到 GameHot generated/bytes/json，再由 `TablesComponent.BuqiConfig.cs` 适配为战斗定义。当前 `2253f0a2` 扩展基线已经推进到 `8 build / 24 法门 / 6 淬炼 / 16 道影`，内容版本为 `buqi-effects-cv1`，并加入 Heal/Regen/Poison/Burn/Freeze 战斗语义。不要再把 9/3/6 写成当前上限。

## 依赖关系

- `Battle` 目录只使用 C# 标准库和仓库内自身类型；不得引用 Unity、UGF、ET、资源、场景、网络、时间或随机 API。
- `Share/Buqi.Simulation.Headless` 以 `Compile Include="..\..\Unity\Assets\Scripts\Game\Hot\Code\Buqi\Battle\**\*.cs"` 链接同一份源码，定义 `BUQI_HEADLESS`，目标 `net8.0`、C# 9，并把 warning 当错误。
- Unity EditMode 测试程序集 `Game.Hot.Buqi.Tests` 只在 Editor 与 `UNITY_GAMEHOT` 下编译，引用 `Game.Hot.Code`、TestRunner、NUnit、UniTask 和 Luban runtime，`noEngineReferences=true`。
- Luban 生成表属于 GameHot 热更 Tables；战斗内核不直接依赖 `DTBuqi*`/`DRBuqi*`，由 `BuqiGeneratedConfigAdapter` 和 `BuqiDefinitionProvider` 转成 `IItemDefinitionProvider`。
- `Design/Buqi_EFFECTS_BUILDS_DB.md` 与 `Design/GAME_DESIGN.md` 是当前内容/阶段证据，不是运行时输入；运行时输入仍以 Excel、generated C#、bytes/json 为准。
- Tuning Register 与 UI 交互方案是设计和验证输入，不是战斗、配置或玩家流程的运行时数据源。

## 入口与调用链

```text
BattleRequest + IItemDefinitionProvider
  -> BuqiBattleSimulator.Simulate
  -> ValidateRequest / BuqiBoardValidator
  -> tick loop: Declare -> Resolve/Chain -> Aggregate -> PostTick
  -> stable BattleResult + BattleLogHash
```

```text
GameHot TablesComponent.LoadAllAsync
  -> generated TablesComponent.LoadAsync(loader)
  -> DTBuqiGlobal / DTBuqiItem / DTBuqiRefinement / DTBuqiEcho
  -> generated PostResolveRef
  -> TablesComponent.BuqiConfig.cs
  -> BuqiGeneratedConfigAdapter.TryReadFromTables
  -> BuqiConfigValidator.Validate
  -> BuqiDefinitionProvider
```

Headless `verify` 和 Unity `ApprovedHashes_MatchCurrentContractVectors` 都读取同一份 `Unity/Assets/Tests/GameHot/Buqi/EditMode/Vectors/approved-buqi-hashes.json`。`verify`/`all` 只读批准基线；只有显式 `update-hashes` 会写入，且写入前仍先执行 `BuqiContractChecks.RunAll()`。

## 核心类型与 API

| 类型/API | 职责 | 生命周期/线程约束 |
| --- | --- | --- |
| `BuqiBattleSimulator` | 战斗主循环、稳定排序、状态效果、日志哈希和结算 | 纯函数式入口；非法请求返回 `InvalidBuild` |
| `BuqiBoardValidator` | 8 格棋盘、实例、尺寸、初始执行/护体/噪声边界 | 进入模拟前的合法性边界；不做运行时归一化 |
| `BuqiContractChecks.RunAll()` | 独立于 approved hash 的行为契约断言 | Hash 更新前必须先通过 |
| `BuqiTestSuite.CreateVectors()` | 15 个稳定向量 | 向量 ID 是批准哈希协议的一部分 |
| `BuqiTestSuite.GenerateStressBuilds()` | 构造确定性压力样本 | 覆盖当前效果族；不表示平衡胜率分布 |
| `BuqiDefinitionProvider` | 将配置行深拷贝为战斗定义 | 返回副本，避免调用方改写缓存 |
| `BuqiConfigValidator` | 校验当前扩展配置链 | 24/6/16 计数、ID 范围、效果字段、引用和棋盘 |
| `BuqiGeneratedConfigAdapter` | 反射读取生成表 | 避免 `Battle` 直接依赖 Luban 生成类型 |
| `BuqiBattleSandbox` | 纸面认知走查用沙盒模型 | Editor-only，不创建正式 UI/prefab |
| `BuqiSandboxWalkthroughBatch` / `Record` / `Export` | 保存同一参与者三轮批次、锁定预测、真实结果、日志证据、归因和改动，并生成稳定导出 DTO | 固定唯一题序、结果曝光锁、会话恢复和成功导出后推进；结构候选不等于 Gate 裁决 |

## 数据与生命周期

- `RuleVersion = 0.4.1`、`SimulationVersion = battle-core-0.4.1` 继续保护原六效果及其 approved hashes；`ContentVersion = buqi-effects-cv1` 在同一 provider 可识别版本下追加 Heal/Regen/Poison/Burn/Freeze，不改写基础契约标识。
- 1 tick = 100 ms，正常 450 tick，600 tick hard cap，单 tick 全场 64 事件、单实例 4 事件上限。
- Charge 0.4.1 在 Declare 阶段完成读取和可选消费：效果已有合法目标后才读取 `ChargeReadLimit`，`ChargeConsume=true` 时立即扣除并记录负数 `ChargeConsumed` Declare-phase 事件；Resolve 只使用 `DeclaredCharge` 快照。
- Declare 队列按 chain depth、来源锚点、来源实例 ID、原始插入顺序排序。同来源多声明因此保持配置/声明顺序，先声明的 Charge 可供后声明读取；A-03 复写复用原声明快照，不二次消费。
- 双方同 tick 的 Declare/Resolve/Chain 全部完成后才 Aggregate，再统一 PostTick 判断胜负；同 tick 双方归零会得到平局，而不是由处理顺序决定胜者。
- Heal 为直接回复执行值且不超过最大执行值；Regen 每 10 tick 进入 Heal 桶；Poison 每 10 tick 直接扣执行值并绕过护体；Burn 每 10 tick 造成可被护体吸收的伤害；Freeze 对目标法门增加冻结 tick，阻断后续冷却推进。
- 历史 Step 3 门禁：`buqi-step3-cv1`，9 个验证法门（`W8-003`、`W8-005`、`W8-006`、`W8-007`、`W8-008`、`W8-012`、`W8-013`、`W8-014`、`W8-015`）、3 个淬炼（A-01、A-03、A-04）和 6 个道影。它只证明最小 Luban 链路，不能再代表当前内容规模。
- 当前扩展基线：`buqi-effects-cv1`，8 个构筑方向（fast、buffer、chain、heal、poison、burn、freeze、overload），24 个法门（`W8-003` 至 `W8-030` 的当前登记集）、6 个淬炼（A-01 至 A-06）和 16 个道影（每个 build 的 lesson/early 快照）。`BuqiConfigValidator`、`BuqiConfigTests` 和真实 generated bytes 适配测试均以此为当前计数。
- `TablesComponent.BuqiConfig.cs` 只在生成表存在时生效；读取失败或业务校验失败直接抛异常，成功后缓存 `BuqiConfig` 与 `BuqiItemDefinitions`。
- P-1 停止线仍有效：自动构筑参与者已完成 3 轮，当前总进度为 3/9；自走棋玩家与新玩家各剩 3 轮。当前扩展基线仍只是战斗与配置局部门禁，不等于已进入正式玩家 UI、完整经济或完整内容体验。
- P-1 窗口默认提供 `fast-space-choice`、`fast-space-choice-buffer-plus`、`fast-space-choice-buffer-plus-a02` 三轮题目；同一参与者批次强制按唯一题序推进，并通过版本化会话 DTO + `SessionState` 跨窗口关闭/domain reload 恢复。预测锁定前禁止运行，结果曝光后禁止清空重开，核心批次只有在当前轮 JSON 文件写入成功并确认后才推进。结果绑定时另存最小曝光墓碑；主会话缺失/损坏或重载后 hash 漂移均失败关闭，替代流程先持久化不同参与者的锁定批次，成功后才删除旧墓碑。
- 跳过预测、普通 Step 2 调试场景或未关联真实 `BattleEvent.Sequence` 的记录可导出诊断，但 `EligibleForGateReview=false`。即使为 `true`，也只表示批次/题序/预测/归因/真实事件 ID 等结构完整；证据相关性、样本计数与 Gate 结论仍由独立评审裁决。

## 开发扩展步骤

1. 修改战斗语义时先更新 `Battle` 代码和 `BuqiContractChecks`，确认行为断言能描述变化，再由人工审阅后显式更新 approved hashes。
2. 新增/修改配置时先改 `Design/Excel/GameHot/Datas/Buqi` 与 schema 表，再运行 Luban Check/Export，检查 Hot generated C#、Hot bytes 和 Editor JSON 同步变化。
3. 新增效果字段必须在 `BuqiConfigModels`、`BuqiGeneratedConfigAdapter`、`BuqiConfigValidator` 与战斗 `BuqiEffectSpec` 的映射中成对落地。
4. 扩充道影要用 `BuqiBoardValidator` 证明 8 格布局、引用、淬炼 ID 和内容版本合法，并用真实 generated bytes 测试证明 fixture 没有和 Excel 分叉。
5. P-1 通过前不得进入正式玩家 UI、完整经济内容或完整内容体验；现有 `Battle Sandbox` 只用于“预测 -> 归因 -> 针对性重构”的认知走查。剩余两类真人各连续三轮，逐轮导出 `EligibleForGateReview=true` 的脱敏 JSON 后交给独立评审；独立评审还必须判断证据相关性与样本有效性。

## 约束与常见错误

- 不要让 `Battle` 反向引用 Luban、Unity、UGF、ET 或资源系统；这会让 headless 编译防线失效。
- 不要把 `update-hashes` 当作普通修复命令。approved hash 只能在契约断言通过、差异经人工确认后刷新。
- `ChargeConsumed` 是 Declare-phase 负数资源事件，不是 Aggregate 日志；把消费推迟到 Resolve/Aggregate 会破坏同 tick 顺序。
- A-03 复写不能重新读取或重复消费 Charge；它必须复用原声明的 `DeclaredCharge`。
- `Check` 只验证 Luban，不生成实际代码/bytes/json；刷新配置必须执行正式导出并检查生成差异。
- 不要用 `production/session-state/active.md` 文件中段的历史状态判断当前源码；`2253f0a2` 已提交 effects/builds，`e8ae61ef` 已提交 P-1 三轮摘要，当前状态以文件末尾为准。
- 本模块记录的 Unity、菜单与 headless 证据是 Buqi 局部门禁，不改变 `runtime-acceptance.json` 五项通用验收的 `not_run` 真实性。

## 验证方法

建议的局部门禁：

1. `dotnet run --project Share/Buqi.Simulation.Headless/Buqi.Simulation.Headless.csproj -- verify`，确认行为契约和 15 个 approved hashes 通过。
2. 需要压力样本时运行 headless `all [count]` 或 `stress [count]`；stress 不读取 approved hash，也不得解释为平衡数据。
3. 在 Unity Editor、`UNITY_GAMEHOT` 下运行 `Game.Hot.Buqi.Tests`，覆盖 Battle、Sandbox、Config 和真实 generated bytes 适配。
4. 通过 Unity 菜单 `Game/Buqi/Battle Sandbox` 打开沙盒，确认默认 P-1 三轮模式、参与者画像、预测锁定、证据事件 ID、备注和 JSON 导出入口可用。
5. P-1 玩家测试时先锁定预测再运行，只把导出 DTO 中 `EligibleForGateReview=true` 的固定题序记录交给独立评审；该字段不是自动计数结论，自动测试或智能体填写不得替代真人样本。
6. 运行 Luban Check/Export 后核对 `dtbuqi*.json`、`dtbuqi*.bytes` 与 generated C# 差异。

本轮主节点已重新验证：既有 Headless Release 证据为 0 warning / 0 error，行为契约与 15 个 approved hashes 全部通过；10,000 个压力构筑得到 10,000 个不同结果，`invalid=0`、`hung=0`。本次 P-1 批次壳修改后 Unity `generation=21`、`errorCount=0`、`warningCount=1`（既有 `TutorialForm.m_SkipButton` 未使用），`Game.Hot.Buqi.Tests` 为 36/36（runId `test-run-f9544836c08343b3b07a6dbab98df9c0`）；沙盒与三个摘要菜单均返回 `executed=true`，三份固定 hash 未漂移，Console error 为 0。本次没有重复运行 Luban 导出或 Headless；五项通用运行验收继续保持 `not_run`，真人 Gate 仍为 3/9。
