# 《The Bazaar / 大巴扎》游戏系统、规则与同类型产品设计研究

**研究日期：2026-08-07**  
**用途：同类型原创游戏立项、原型与数据架构参考**

> 重要声明：The Bazaar 是持续更新的在线游戏。本文把“官网直接可见内容”“2026 年社区资料”“旧版本资料或合理推断”分开标注。随补丁变化的数值必须在使用前复核。附带的数据文件来自非官方社区数据库，只能用于研究、统计与原型验证，不能当成官方实时数据，也不应直接复制名称、文本、美术、角色或数值用于商业发行。

## 1. 执行摘要

The Bazaar 的核心不是传统抽牌，而是一个**异步 PvP + 自动战斗 + 商店构筑 + Roguelite 路线选择**系统：玩家在每个 Day 的若干 Hour 中访问商人、训练师、事件或 PvE，持续调整有限棋盘；Day 末与同进度玩家的“幽灵阵容”自动战斗。目标通常是先取得 10 次 PvP 胜利，PvP 失败则损失 Prestige（局外生命线）。

最值得借鉴的五个支柱：

1. **时间即行动点**：每次购物或事件消耗一个 Hour，选择本身就是机会成本。
2. **空间即构筑成本**：Small / Medium / Large 物品占据不同格数，强度不只由稀有度决定。
3. **触发器网络而非卡组循环**：物品通过冷却、邻接、类别与状态形成“自动运行机器”。
4. **异步 PvP 降低联网压力**：服务器只需保存可验证阵容快照和战斗种子，不要求双方同时在线。
5. **高变化、低操作负担**：策略集中在战前；战斗自动执行，使复杂联动仍可观看和理解。

对原创同类产品，建议保留“时间—空间—触发器—异步快照”四层骨架，但必须替换世界观、英雄、资源、术语、卡牌文本、美术、数值曲线和具体事件。不要只做换皮。

## 3. 核心游戏循环

### 3.1 单局目标

- 玩家选择一名英雄，进入一条由多个 Day 构成的 Run。
- 每日通过商店、事件、训练师、PvE 等获取或强化物品与技能。
- 每日末与同 Day 的玩家幽灵阵容进行异步 PvP。
- 常见目标为先获得 **10 次 PvP 胜利**。
- 旧版且多源一致的 Prestige 规则：初始 20；PvP 失败损失等于当前 Day 的 Prestige；归零后获得一次“最后机会”事件，再次输掉 PvP 则 Run 结束。此精确数字来自 2025 指南，当前客户端需复核。

### 3.2 Day / Hour 结构

旧版公开指南描述每个 Day 有 6 个 Hour：

1. Hour 1、2：商店 / 事件 / 奖励选择
2. Hour 3：三选一 PvE 怪物
3. Hour 4、5：商店 / 事件 / 奖励选择
4. Hour 6：异步 PvP

该结构很好地把一次完整决策循环压缩成：**建设 → 风险测试 → 再建设 → PvP 验收**。但 Hour 数量和节点位置可能随版本变化；开发同类产品时应把时间轴完全数据化，而不是写死。

### 3.3 一局的决策闭环

1. 观察当前阵容短板和下一个已知节点。
2. 在多个事件之间选择：买即时战力、投资经济、拿经验、赌稀有奖励或打 PvE。
3. 调整主棋盘与 Stash，处理格子和出售价值。
4. 自动战斗，获得胜负反馈。
5. 根据战斗日志判断：缺伤害、缺生存、启动过慢、被控制、资源耗尽或触发链断裂。
6. 下一 Day 修正构筑，直到 10 胜或 Prestige 耗尽。

## 4. 局内系统拆解

### 4.1 英雄与独立卡池

2026-08-06 的 Mobalytics 英雄页列出 8 个可玩英雄：

| 英雄 | 定位标签 | 典型方向 | 资料状态 |
|---|---|---|---|
| Vanessa | Seafaring Rogue | Ammo、Poison、Burn、武器、水系 | Base |
| Pygmalien | Entre-Pig-Neur | Economy、Property、Health、价值成长 | Base |
| Dooley | AI Robot | Core、Tech、Burn、Friend | Base |
| Mak | Alchemical Immortalist | Potion、Transform、Regen | DLC |
| Stelle | Bright Aeronaut | Flying、Haste、Vehicle | DLC |
| Jules | Chef of the Deeps | Food、Burn、Freeze | DLC |
| Karnok | Monstrous Hunter | Rage/Enrage、Friends、Ammo | DLC |
| The Dragons | 多角色/乐团式机制 | Tempo、Notes、Instrument、Dragon | DLC；2026 新资料 |

The Bazaar Wiki 的英雄页只列前 7 名，而 Mobalytics 2026-08-06 已加入 The Dragons，说明数据库之间存在版本延迟。离线静态库覆盖前 7 名，不含 The Dragons。

**设计意义**：英雄不是简单皮肤，而是内容池过滤器 + 独有规则入口。这样同一套底层战斗系统可以通过不同英雄产生显著不同的学习曲线和构筑语法。

### 4.2 棋盘、尺寸与 Stash

旧资料中：

- 物品有 Small、Medium、Large 三种尺寸，分别占 1、2、3 格。
- 主棋盘早期较小，升级后扩张，旧版上限常见为 10 格。
- Stash 用于保留备选物品；部分“战斗外”效果在 Stash 中仍会生效。
- 邻接、最左/最右、相对位置是大量效果的条件。

**设计意义**：尺寸把“卡牌费用”从一次性法力改成持续占用的空间预算。大型物品必须与多个小型联动件竞争位置，这天然产生取舍。

### 4.3 物品、技能、等级与附魔

- 物品是棋盘上的主动或被动组件，可含冷却、弹药、伤害、治疗、护盾、状态、触发器与类型标签。
- 技能通常不占棋盘格，提供全局或条件被动。
- 物品有 Bronze、Silver、Gold、Diamond 等等级；Legendary 常用于特殊掉落或遭遇物品。
- Upgrade 提高等级，通常增强数值、持续时间、目标数或冷却。
- Enchantment 为物品叠加新效果或改变原效果。近期社区库中常见 13 种：Golden、Heavy、Icy、Turbo、Shielded、Restorative、Toxic、Fiery、Shiny、Deadly、Radiant、Obsidian、Mossy。

### 4.4 商店、经济与出售

- Gold 是局内购买与刷新资源。
- Income 提供周期性经济，鼓励在即时战力与复利之间选择。
- 商人具有不同物品池约束：英雄、尺寸、类型、等级、是否武器等。
- 物品可在整备阶段出售；部分物品通过“出售”触发永久成长、生成物品或特殊事件。
- 近期离线库记录 47 名商人、23 名训练师；说明商店不是一个统一随机池，而是多个可控子池。

### 4.5 经验、等级与成长

经验来自推进节点、PvE 和事件。升级通常带来：

- 最大生命成长；
- 早期棋盘空间扩张；
- 三选一升级奖励；
- 特定等级的技能、物品升级、附魔或英雄专属奖励。

2025 的等级奖励表曾经历多次改版，不能直接作为当前数值规格。对原创产品，应把 `LevelRewardTable` 与英雄覆写做成数据配置。

### 4.6 PvE、事件与风险选择

- PvE 通常三选一，难度和奖励不同。
- 胜利可提供 Gold、XP，以及怪物专属物品或技能。
- 失败一般不会像 PvP 那样直接扣 Prestige，但会失去奖励并造成成长落后。
- 事件提供资源交换、随机奖励、永久增益、物品生成或特殊商店。
- 近期静态库：121 怪物、49 事件、413 个事件步骤，说明“事件选择结果”应独立建模，不能只存一段描述文本。

### 4.7 异步 PvP 与幽灵快照

- 对手是其他玩家在相同 Day 或相近进度提交的阵容快照。
- 本地或服务器按确定性规则重放战斗。
- 这种模式兼顾真人构筑的不可预测性与单人随时暂停的体验。

实现关键：

1. 服务端保存快照版本、英雄状态、物品实例、技能、位置、永久堆叠、随机种子和规则版本。
2. 客户端只提交输入，不提交“我赢了”的结果。
3. 战斗引擎必须确定性；相同输入与版本必须得到相同结果。
4. 补丁后旧快照要么按旧版本模拟，要么失效，不能混用规则。

## 5. 自动战斗与关键词规则

以下机制主要来自 Mobalytics 2026-03-12 关键词指南，并与近期卡牌文本交叉核对。

| 关键词 | 规则摘要 | 实现注意 |
|---|---|---|
| Cooldown | 物品充能完成后使用 | 使用后重置；可被 Haste/Slow/Charge 影响 |
| Ammo | 弹药耗尽后停止充能；战斗后补满 | Multicast 是否额外耗弹须由能力定义统一处理 |
| Charge | 立即推进物品冷却进度 | 不等于 Haste；是一次性时间跳跃 |
| Haste | 物品充能速度变为 2 倍 | 与 Slow 同时存在时需定义叠加或抵消顺序 |
| Slow | 物品充能速度变为 0.5 倍 | 影响持续时间应由状态实例管理 |
| Freeze | 冻结期间不充能且不能使用 | 被动效果是否继续生效需按 Destroy 区分 |
| Flying | Flying 物品受到的 Slow/Freeze 持续时间减半 | 是标签/状态混合机制，支持战斗中开始 Flying |
| Damage | 对生命造成直接伤害，先由 Shield 阻挡 | Poison 例外；Burn 与 Shield 有特殊交互 |
| Shield | 阻挡 Damage；Poison 绕过；对 Burn 伤害减免 50% | 需明确同一 tick 的结算顺序 |
| Heal | 恢复生命至上限，并清除 10% Poison 与 Burn | 百分比取整规则要固定 |
| Regen | 每秒按 Regen 值恢复生命 | 可被暴击；属于战斗内可成长数值 |
| Burn | 每秒触发两次伤害；每次结算后层数 -1 | Shield 对其减伤 50% |
| Poison | 每秒伤害，绕过 Shield | 页面未说明每 tick 是否衰减，应以当前客户端为准 |
| Crit | 有冷却物品的主动效果概率翻倍 | 可翻倍 Damage、Heal、Shield、Regen、Burn、Poison |
| Multicast | 一次使用让效果重复执行多次 | 每次子效果的触发、暴击、目标与弹药必须统一定义 |
| Destroy | 物品完全失效：不能主动，也失去被动 | 与 Freeze 不同；Repair 可恢复 |
| Repair | 使一个 Destroyed 物品恢复功能 | 目标选择和状态清理顺序要确定性 |
| Transform | 变成相同尺寸的随机物品，通常受英雄池约束；可保留适用附魔 | 必须使用可回放随机种子 |
| Rage | Karnok 使用物品累积 Rage；达到 100 触发 Enrage | 英雄专属资源 |
| Enrage | 清除己方物品 Slow/Freeze，5 秒内冷却缩短 10% | “冷却缩短”应区分基础冷却和当前进度 |

### 5.1 推荐的结算流水线

建议同类产品采用固定事件队列：

1. 推进模拟时钟到下一个事件时间。
2. 更新所有状态持续时间和充能。
3. 将同时间点完成充能的能力按稳定优先级入队。
4. 支付成本（弹药、资源、销毁自身等）。
5. 选择目标。
6. 计算暴击与倍率。
7. 应用主效果。
8. 派发 `OnUse / OnDamage / OnShield / OnHaste / OnCrit / OnDestroyed` 等事件。
9. 将连锁触发继续入队，设置每帧/每事件链上限防止无限循环。
10. 检查双方死亡与超时规则。

不要把卡牌文本直接写成任意脚本执行。应采用受控的效果图或指令列表，保证可验证、可回放和可平衡。

## 7. 数值与构筑结构

### 7.1 典型构筑轴

- **前置爆发**：短冷却、多重释放、暴击、弹药；目标是在对手引擎启动前结束战斗。
- **持续伤害**：Burn / Poison；通过高频触发和状态放大越过或削弱防御。
- **护盾反击**：Shield 堆叠后转化为 Damage，或拖到超时压力阶段。
- **治疗再生**：Heal / Regen / 最大生命，依靠净化与成长对抗持续伤害。
- **控制锁**：Haste 自己、Slow/Freeze 对手，以充能差建立行动压制。
- **经济成长**：Value、Income、Property、出售触发；牺牲前期换中后期资源优势。
- **召唤/伙伴**：Friend、生成物、复制、Transform，靠数量和触发密度形成网络。
- **位置引擎**：相邻、左侧、右侧、最慢/最快目标；通过棋盘排序优化。
- **英雄资源**：Core、Flying、Food、Potion、Rage、Tempo/Notes 等专属语法。

### 7.2 平衡公式建议

不要只用 DPS 衡量物品。每件物品应计算多维预算：

```text
PowerBudget =
  DirectOutput
+ TempoValue
+ ScalingValue
+ EconomyValue
+ FlexibilityValue
+ ReliabilityValue
- SpaceCost
- SetupCost
- OpportunityCost
- CounterplayRisk
```

其中：

- `DirectOutput`：伤害、盾、治疗、状态的等价值；
- `TempoValue`：Haste、Slow、Freeze、Charge 对行动次数的影响；
- `ScalingValue`：永久堆叠和战斗内成长；
- `FlexibilityValue`：标签数量、英雄池通用性、目标选择；
- `ReliabilityValue`：不依赖随机目标或特定组合的稳定性；
- `SpaceCost`：占格数及对邻接布局的挤压；
- `SetupCost`：启动时间、弹药限制、触发前提；
- `CounterplayRisk`：易被 Freeze、Destroy、Poison 等克制。

### 7.3 反无限循环

- 每个根事件设置最大派生事件数，例如 256。
- 同一能力在同一根事件链中设置触发上限。
- 禁止“由自身派发的同类事件再次无条件触发自身”，除非显式设置 cooldown 或次数。
- 服务器检测循环签名：`source + trigger + target + stateHash` 重复过多则截断。
- 把截断原因写入战斗日志，便于调试和玩家理解。

## 8. 同类型原创游戏方案

### 8.1 建议保留的抽象

- 每日有限行动点；
- 主棋盘空间预算；
- 自动战斗；
- 事件与商人子池；
- 异步 PvP 幽灵；
- 英雄独立内容池；
- 标签驱动的组合构筑；
- 可观看、可回放的确定性战斗。

### 8.2 必须原创化的部分

- 世界观、角色名称和视觉轮廓；
- 资源名称、状态关键词、UI 布局与动画语言；
- 每个英雄的独有资源和构筑语法；
- 卡牌名称、文本、数值、插画、图标、音效；
- Day 节奏、胜负目标、失败资源；
- 事件文案与选择结果；
- 商业化、奖励和排位结构。

### 8.3 一个可行的原创差异化方向

**主题：移动城邦的“工坊远征”**

- 玩家扮演不同职业的工坊领航员，而非商人英雄。
- 棋盘是 12 个“动力接口”，组件占 1–4 接口。
- 每日不是固定 6 Hour，而是 8 点“燃料”；普通事件耗 1，远征耗 2，黑市耗 3。
- 战斗资源改为 Heat / Pressure / Signal，三者互相制约。
- 异步 PvP 目标不是 10 胜，而是在 12 天内累计“航路声望”，失败增加“船体裂纹”；可用资源修复。
- 英雄独有机制示例：过热连锁、压力储能、无人机编队、生态培养、信号干扰。

这样保留可验证的市场需求与核心体验，又形成独立的玩法表达。

## 9. Unity 技术架构建议

### 9.1 模块边界

```text
Domain
├─ RunState / DayTimeline / EncounterResolver
├─ Inventory / Board / Stash / Shop
├─ ItemDefinition / ItemInstance / SkillDefinition
├─ CombatWorld / Combatant / AbilityRuntime
├─ Effect / Trigger / TargetSelector / Status
├─ DeterministicRng / EventQueue / CombatLog
└─ Snapshot / Replay / RuleVersion

Application
├─ StartRun / ChooseEncounter / Buy / Sell / Reroll
├─ ArrangeBoard / StartCombat / ResolveRewards
└─ SubmitGhost / FetchOpponent / VerifyResult

Infrastructure
├─ Addressables / Localization / Save
├─ RemoteConfig / ContentVersion
├─ BackendApi / GhostStorage / Telemetry
└─ DataImport / Validation / BalanceSimulation
```

### 9.2 数据驱动原则

- ScriptableObject 可做编辑器资产，但运行时权威数据应能导出为 JSON/二进制表。
- 所有效果使用稳定 ID，不用类型名作存档协议。
- 触发器与效果采用组合式节点，而非每张卡一个 C# 类。
- 战斗核心避免依赖 Unity `Update`、浮点非确定性和物理引擎。
- 使用整数 tick 或定点数，例如 1 秒 = 1000 tick。
- 所有随机调用经过命名随机流，记录调用序号。
- 战斗日志输出事件 ID、来源、目标、前后状态和规则版本。

### 9.3 服务端最小需求

- 账号与 Run 存档；
- 内容版本与远程配置；
- 幽灵快照上传、匹配和过期；
- 服务端或可信模拟器验证战斗；
- 排位、奖励与反作弊；
- 统计埋点：选择率、购买率、上场率、胜率、平均 Day、组合共现率。

## 10. MVP 开发范围

### 阶段 A：战斗沙盒

- 1 名英雄；
- 40–60 个原创物品；
- 15 个技能；
- 10 个关键词；
- 棋盘 + Stash + 自动战斗 + 日志；
- 可输入固定种子并重放。

验收：1000 次同种子模拟结果完全一致；无无限循环；一场战斗可逐事件回看。

### 阶段 B：单机 Run

- 6 Day；
- 12 个商人/训练师；
- 15 个 PvE；
- 20 个事件；
- Gold、Income、XP、Level、升级、附魔；
- 本地 AI 或录制快照代替真人幽灵。

### 阶段 C：异步 PvP

- 快照服务；
- 按 Day、隐藏强度分和版本匹配；
- 服务器验证；
- 战斗回放；
- 基础赛季和奖励。

### 阶段 D：内容扩展

- 3 名英雄；
- 每名 80–120 物品 + 通用池；
- 内容编辑器、校验器、批量模拟器；
- 远程热修和版本兼容。

## 11. 测试与数据分析

必须自动化的测试：

1. 所有定义 ID 唯一、引用存在、等级数组长度合法。
2. 每张物品在所有 Tier 和附魔组合下可实例化。
3. 战斗确定性：跨机器、跨帧率、跨运行一致。
4. 触发器链上限和循环检测。
5. 死亡、同时死亡、超时、护盾/Burn/Poison 边界。
6. Transform、复制、Upgrade 后实例状态正确。
7. 旧快照遇到新规则版本时明确拒绝或迁移。

核心平衡指标：

- 物品出现率、购买率、出售率、上场率；
- 上场条件胜率与调整后胜率；
- 首次获得 Day、平均持有时长；
- 组合共现提升度；
- 触发次数、有效输出、过量治疗/护盾；
- 英雄 10 胜率、平均结束 Day、Prestige 分布；
- 商人/事件选择率与机会成本。

不要仅按单卡胜率削弱，因为高胜率可能来自稀有度、获得时点或只在优势局被选择。

## 12. 法务与合规边界

可借鉴的是抽象玩法机制，不能复制具体表达。应避免：

- 使用 The Bazaar、大巴扎、英雄名、卡名、原文卡牌描述作为商业内容；
- 复制角色形象、UI 构图、图标、音效、美术或宣传素材；
- 大规模内置第三方数据库或图片并随产品分发；
- 宣称社区数据为官方授权；
- 通过抓取绕过访问控制或违反站点条款。

建议在立项后做一次知识产权律师评审，保存原创设计演化记录，并对角色、美术和命名做商标检索。

## 13. 结论与建议

1. The Bazaar 的护城河不是“卡多”，而是**有限时间 + 有限空间 + 自动触发网络 + 真人幽灵**的组合。
2. 原型首先验证确定性战斗和卡牌编辑工具，而不是先做大量内容或联网大厅。
3. 首版只做 1 名英雄、50 张左右原创物品，先证明至少 5 条可辨识构筑轴。
4. Day / Hour、等级奖励、附魔、商人池和状态规则必须全部数据化，便于高频改版。
5. 使用本次 1061 物品离线库研究字段分布和内容密度即可，不要复制其文本和数值。
6. 对 2026 最新版本，The Dragons 和 z17.0 内容仍需单独增量抓取与人工校验；任何“全卡牌”交付都必须附版本号与覆盖说明。
