# 知识库 Loop 协议

## 目标

每个 Loop 只处理一个边界清晰的模块或一组强相关模块，但必须留下可验证的增量：源码证据、模块文档、目录状态和校验结果同步更新。

## 单轮流程

1. **选择缺口**：从 `catalog.json` 中优先选择 `planned`，其次选择 `seed`。不要只按文档编号顺序；优先处理后续开发依赖最多的模块。
2. **确定边界**：确认模块的程序集/项目、源码目录、上游依赖、下游调用者、生成物和编辑器入口。
3. **阅读源码**：至少检查入口类、核心接口、生命周期实现、配置与一处真实调用。`Book/` 和旧文档只能辅助理解。
4. **编写文档**：使用 `_template.md` 的固定章节。所有文件引用使用仓库相对路径，所有命令注明执行目录。
5. **交叉核验**：确认示例 API 在当前源码存在；确认手工修改入口与生成目录没有混淆；记录条件编译符号和模式差异。
6. **更新目录**：只有模板必填项和源码核验完成后，才能把模块状态改为 `verified`。
7. **刷新与校验**：源码核验完成后执行 `Test-KnowledgeBase.ps1 -RefreshSourceFingerprints`，审查生成的指纹变化，再执行普通与 `-RequireStaticComplete` 校验。修复错误后提交本轮结果，并在下一轮重新读取源码状态。

## `verified` 准入条件

- `catalog.json` 中声明的所有 `sources` 当前存在。
- 文档明确说明：职责与边界、入口与调用链、核心类型/API、数据或生命周期、扩展步骤、约束与常见错误、验证方法。
- 至少给出一个来自仓库的实际调用点或配置入口。
- 涉及 ET/GameHot、客户端/服务端、热更/非热更时，明确适用模式。
- 涉及生成代码时，标出源文件、生成命令/菜单和生成目标，且明确禁止手改的目录。
- 文档结论来自当前源码；无法证实的内容明确写为“待确认”，模块保持 `seed`。
- 文档头必须逐项列出映射到该文档的全部 Catalog ID、`verified` 状态、有效核验日期和非空适用模式；权威源内容必须与 `source-fingerprints.json` 一致。

## AI 开发调用约定

收到开发需求后，AI 应先从 `catalog.json` 选择模块，再读取对应文档和源码。实现结束后，如果模块入口、流程、配置或约束发生变化，应在同一变更中更新知识库，防止知识层与代码分叉。

建议检索顺序：

```text
需求关键词
  -> catalog.json 的 name/keywords/area
  -> 对应模块文档
  -> sources 中的入口源码
  -> 调用点与测试/编辑器验证
```

## 完成判定

“静态知识层完成”必须同时满足：

1. `Test-KnowledgeBase.ps1 -RequireStaticComplete` 返回成功。
2. 模块目录覆盖全部仓库内自研程序集、项目和工具入口。
3. 没有遗留 `planned`、`seed` 或文档中的“待确认”。

“知识库全流程完成”还必须同时满足：

1. 抽样执行客户端启动、服务端启动、Luban 导表、Proto 生成和目标 Player 构建，文档与实际行为一致。
2. 在 `runtime-acceptance.json` 记录执行时间、环境、源码 revision 和仓库内证据，五项状态均为 `passed`。
3. `Test-KnowledgeBase.ps1 -RequireComplete` 返回成功；源码 revision 之后运行相关路径不得有变更或未提交修改。
