# 《不器》可行性说明

## 总体结论

《不器》在严格控制范围的前提下可行。

设计和制作评估为“有条件可行”，技术评估为“可执行”。共同结论是：

> 首先制作本地离线对手快照原型。最小版本不制作真实在线对战、服务器匹配、大规模美术，也不改成战斗中手动出牌的传统牌组构筑。

## 核心可行性

只有当玩家能清楚理解以下循环时，核心才成立：

1. 组装一套自动构筑。
2. 观看它与对手快照交战。
3. 理解主要胜负原因。
4. 根据原因调整下一场构筑。

如果第三步失败，游戏会变成难以阅读的自动播放；如果第四步失败，肉鸽单局便失去意义。

## 最小版本边界

| 项目 | 目标 |
|---|---|
| 单局时长 | 8-12 分钟 |
| 单场战斗 | 30-45 秒，60 秒硬上限 |
| 获胜条件 | 获得 5 枚胜场 |
| 失败条件 | 3 点单局生命，每次战败失去 1 点 |
| 装备 | 18 个 |
| 改造 | 6 种 |
| 构筑方向 | 3 种清晰方向 |
| 对手快照 | 12 份离线快照 |
| 在线对战 | 不进入最小版本 |

## 原型必须证明的事情

1. 玩家看完战斗后，能够说出一个主要胜负原因。
2. 玩家会在下一次购买或改造时，根据这个原因修改构筑。
3. 不同对手快照表现为不同构筑，而不是随机数值墙。

## 技术方向

- 在 Unity 内构建，以便验证完整玩家循环。
- 战斗模拟保持为纯确定性 C#，不依赖 `UnityEngine`、UGF、ET、动画、帧率或 Unity 随机数。
- 输入为 `player BuildSnapshot + echo BuildSnapshot + seed`。
- 输出为 `BattleResult + BattleLog`。
- 由 `BattleLog` 驱动回放界面、暂停、变速、效果高亮和败因总结。

最小版本使用手工制作的离线对手快照，并可补充本地历史构筑。匹配依据为轮次、棋盘占用、胜场数量、难度标签和构筑方向。

## 主要风险

| 风险 | 应对方式 |
|---|---|
| 自动战斗难以阅读 | 尽早制作回放、暂停、变速、触发日志和战后总结 |
| 失败显得随机 | 战前公开对手方向、关键装备和主要威胁 |
| 环境收敛为唯一最优构筑 | 在扩内容前先验证方向压力、反制空间和改造代价 |
| 内容扩张过快 | 使用较少装备形成更多联动，延后身份和完整剧情 |
| 后端消耗个人开发时间 | 核心乐趣得到证明前，全部对战使用离线对手快照 |

## 首批开发任务

| 优先级 | 任务 | 产物 |
|---|---|---|
| 1 | 定义战斗规则契约 | 时间、触发阶段、目标、胜负、平局、随机和循环上限 |
| 2 | 定义数据对象 | 装备定义、实例、改造、构筑快照、战斗请求、结果和日志 |
| 3 | 实现确定性模拟核心 | 带种子复现的纯 C# 战斗引擎 |
| 4 | 制作首批内容 | 18 个装备、6 种改造、3 个构筑方向 |
| 5 | 制作离线对手快照池 | 12 份教学、前期、成型和混合构筑 |
| 6 | 构建单局循环 | 商店、购买、升级、改造、战斗、奖励和单局生命/胜场结算 |
| 7 | 构建战斗回放 | 自动播放、暂停、变速、触发日志和关键效果高亮 |
| 8 | 构建调试与模拟工具 | 选择对手快照、固定种子、批量模拟和导出日志 |
| 9 | 进行首次试玩 | 验证玩家能否理解胜负并据此调整构筑 |

详细执行顺序见[首个可玩原型计划](buqi-prototype-plan.md)，玩法规则来源见[玩法规格 v0.4](buqi-gameplay-spec.md)，模拟规则见[确定性战斗契约 v0.4.1](buqi-battle-contract.md)。

## 最小版本明确不做

- 实时对战和服务器端匹配。
- ET 房间与会话流程。
- 使用 MongoDB 保存玩家对手快照。
- 排行榜、赛季、反作弊和社交关系。
- 大量角色立绘、复杂场景或完整五章剧情演出。
- 传统的抽牌、手牌管理和战斗中主动出牌。
