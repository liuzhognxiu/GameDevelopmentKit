# 02｜棋盘、装备、品质与改造系统 v0.5

> 状态：v0.5（2026-08-23）。术语遵循 `gameplay-terminology.md` v1.2 双层——本文用**游戏术语**（装备 / 仓库 / 减速 / 护盾反击），剧情用包装术语（器物 / 仓位 / 迟滞 / 护盾反制）。
> 相对旧版（v0.4.1）的关键改动：棋盘 8→10 格线性、仓库 5→10 格、品质改"每个品质单独配置"、构筑方向 3→8 种、装备数据结构增 `Hero` 字段与新关键词。

## 1. 系统卡

| 字段 | 定义 |
|---|---|
| Purpose | 用 10 格空间把"拿到好东西"转化为"愿意为哪条运转关系付出位置" |
| Player experience goal | 玩家能指出一个因尺寸、相邻或空格产生的真实得失 |
| Inputs | ItemDefinition、ItemInstance、BoardCommand、仓库状态 |
| Outputs | 合法 BoardState、规范化 BuildSnapshot、失败原因 |
| 核心边界 | 棋盘制造选择，不估算战力；UI 不自动替玩家优化布局 |

## 2. 棋盘与仓库

- **棋盘**：10 格线性，编号 0–9。[待定] 拓扑（线性/环形）由用户后续调整，当前按线性；现有代码为 8 格环形，属待同步的新目标值。
- **占位**：S/M/L 分别占 1/2/3 个连续格。
- **仓库**：10 格，每格存 1 个实例，不读取尺寸。
- **相邻关系**：沿线性顺序建立（左/右各一）；[待定] 随拓扑调整后同步。
- 空格合法，并阻断相邻。
- 多格装备锚点始终是最左占位。

### 设计职责

| 尺寸 | 玩家问题 | 内容职责 | 失败信号 |
|---|---|---|---|
| S | 要不要用灵活性换单卡效率？ | 启动、填位、局部辅助 | 小卡海无条件最高效 |
| M | 哪个关系值得当枢纽？ | 主力、转化、双边相邻 | 所有方向都必带同一 M |
| L | 愿意为改变全局节奏放弃什么？ | 核心规则、终结、结构重排 | 只是三格大数字 |

## 3. BoardCommandService

### 命令

- `Place(instanceId, anchorSlot)`
- `Move(instanceId, anchorSlot)`
- `Swap(firstId, secondId)`
- `ReturnToStorage(instanceId)`
- `DeployFromStorage(instanceId, anchorSlot)`
- `AutoMerge(sourceIds)`：只处理合并规则，不自动改其他布局

### 失败原因

`OutOfBounds`、`Overlap`、`StorageFull`、`InstanceMissing`、`InstanceAlreadyPlaced`、`WouldOrphanPurchase`、`InvalidStateRevision`。

错误位置保持原状态，不自动挤压。自动挤压看似贴心，实则替玩家做了空间决策。

## 4. 装备数据结构

```text
ItemDefinition
- id, displayName, size, basePrice
- hero            // 英雄归属：0=通用，1~4=英雄
- tags[]
- baseCooldownTicks
- ammoCapacity    // 0=无限弹药
- triggers[]
- effects[]
- contentVersion
- readableSummaryKey

ItemInstance
- instanceId, definitionId
- quality
- refinementId?
- anchorSlot? / storageIndex?
- temporaryModifiers[]
```

> `hero` 字段支撑英雄专属卡池过滤（详见 `buqi-heroes.md` v0.1）；`ammoCapacity` 及 暴击/多重/弹药/飞行/价值 关键词对齐契约 v0.7.0。

### 装备设计模板

每张装备必须填：

| 字段 | 问题 |
|---|---|
| Purpose | 它在什么构筑问题里提供新解法？ |
| Decision | 玩家放它时舍弃什么？ |
| Trigger | 玩家能否在战前预测触发？ |
| Output | 它改变伤害、护盾、节奏还是充能？ |
| Dependency | 需要位置、标签、状态还是敌方结构？ |
| Counterplay | 哪类对手快照使它表现下降？ |
| Failure state | 空转、过慢、占位浪费如何被看见？ |
| Tuning levers | cost/reward/duration/cooldown 各由什么假设支撑？ |

禁止只写"强力核心""高额伤害"这类无法实现也无法测试的形容词。

## 5. 品质与合并

- 品质分档：普通、改良、定型三档（档数 [可调]）。
- **每个品质单独配置**：同名不同品质是**独立配置条目**（各自 basePrice / 数值 / 效果），不做全局倍率（废弃旧版 1.00/1.60/2.40 倍率）。
- **合并**：两张同名同品质自动合并 → 升级到下一品质；普通升到定型需 4 个普通副本。合并保留棋盘实例及位置；多个改造时由玩家选择保留一个。
- 品质升级 = 切换到对应品质的独立配置。

### 品质的设计红线

1. 不能因品质提升让原本带代价的改造变成无代价。
2. 不能让同名追卡成为所有经济状态下的最佳 sink。
3. 不能通过改冷却偷偷改变整条触发顺序，除非卡面明确并升级规则版本。

## 6. 改造

每个实例最多 1 个改造；覆盖旧改造是不可逆选择，旧改造不返还价值。

| 改造 | Gain | Sink / 代价 | 制造的新决策 | 核心失败信号 |
|---|---|---|---|---|
| 高速 | 冷却 -15% | 效果量 x0.85 | 快但弱是否值得 | 低频卡白拿速度，代价不发生 |
| 强效 | 冷却 +20%，效果 +30% | 启动变慢，开战效果不增幅 | 单次质量 vs 周期次数 | 长战斗中收益无条件覆盖成本 |
| 复制 | 首次主动后 50% 追加 | 不触发相邻响应，不二次消费 | 爆发 vs 连锁价值 | 复制复杂链导致隐式二次消费 |
| 抗减速 | 免疫敌方减速 | 不能获友方加速 | 针对性稳定 vs 自身上限 | 无减速环境仍是最优 |

> 改造由 6 项收为 **4 项**（删除依赖过载的"稳定 / 超载"）；"高速"的代价由"每次+过载"改为"效果量降低"。百分比与代价语义 [待核对] 当前契约与 Luban 表；代价结构（复制不触发相邻、抗减速拒绝友方加速）不得用调数值改掉，需走规则版本与断言评审。

## 7. 七种构筑方向

构筑方向是分析标签，不是职业锁。

| Build | 中文包装 | 核心计划 | 被克制点 |
|---|---|---|---|
| fast | 攻击快攻 | 用加速和充能提前打出伤害窗口 | 护盾、冰冻 |
| buffer | 护盾反击 | 先叠护盾，再用护盾破裂触发反击 | 中毒 |
| chain | 充能连锁 | 依靠相邻装备互相充能，放大核心攻击 | 冰冻、减速 |
| heal | 治疗续航 | 用治疗和再生熬过爆发 | 中毒、冰冻核心治疗 |
| poison | 中毒消耗 | 无视护盾压低生命，逼对手带治疗 | 快攻 |
| burn | 灼烧压迫 | 持续消耗护盾，再用攻击压死 | 大护盾、治疗 |
| freeze | 冰冻控制 | 冻住敌方关键装备，打乱出手节奏 | 多小件分散目标 |

## 8. Edge Cases

- 满盘/满仓：只允许购买会立即合并的装备。
- 合并后尺寸不变，原位置仍需合法。
- 覆盖改造前必须二次确认，并展示失去的规则，不展示虚构"战力变化"。
- 同一实例不能同时在棋盘和仓库。
- 空格是策略状态，不提示为"未完成布局"。
- 多格装备旋转不进入首阶段。

## 9. Failure States

- 自动推荐布局压缩探索。
- 卡面必须展开三级详情才能理解主触发。
- 大型装备采用率低，因为其效果没有改变全局节奏。
- 所有获胜构筑趋向满 10 格，空格从不成立。
- 改造代价只存在于文字，样本中极少实际触发。

## 10. Acceptance

### 功能

- 所有命令确定性、可撤销到提交前状态，并返回明确失败原因。
- 规范化快照在 PC/移动逻辑层一致。
- 空格、相邻、多格占位与合并覆盖全部单元测试。

### 体验

- 玩家面对同一对手快照时，至少能提出两种格位成本不同的合法布局。
- 玩家能预测一项改造的收益窗口和账单窗口。
- 代表样本中不存在仅因单位格效率而垄断所有方向的尺寸。
