# 02｜周天盘、法门、品质与淬炼系统

## 1. 系统卡

| 字段 | 定义 |
|---|---|
| Purpose | 用 8 格空间把“拿到好东西”转化为“愿意为哪条运转关系付出位置” |
| Player experience goal | 玩家能指出一个因尺寸、相邻或空格产生的真实得失 |
| Inputs | ItemDefinition、ItemInstance、BoardCommand、仓位状态 |
| Outputs | 合法 BoardState、规范化 BuildSnapshot、失败原因 |
| 核心边界 | 棋盘制造选择，不估算战力；UI 不自动替玩家优化布局 |

## 2. 周天盘

- `[SCOPE]` 8 个连续格位，编号 0–7。
- `[SCOPE]` S/M/L 分别占 1/2/3 个连续格。
- `[PLACEHOLDER]` 仓位 5 格，每格存 1 个实例，不读取尺寸。
- 空格合法，并阻断相邻。
- 多格法门锚点始终是最左占位。
- 两个法门即使接触多个边界，也只建立一次相邻关系。

### 设计职责

| 尺寸 | 玩家问题 | 内容职责 | 失败信号 |
|---|---|---|---|
| S | 要不要用灵活性换单卡效率？ | 启动、填位、局部辅助 | 小卡海无条件最高效 |
| M | 哪个关系值得当枢纽？ | 主力、转化、双边相邻 | 所有方向都必带同一 M |
| L | 愿意为改变全局节奏放弃什么？ | 核心规则、终结、结构重排 | 只是三格大数字 |

## 3. BoardCommandService

### 命令

- `Place(instanceId, anchorSlot)`
- `Move(instanceId, anchorSlot)`
- `Swap(firstId, secondId)`
- `ReturnToStorage(instanceId)`
- `DeployFromStorage(instanceId, anchorSlot)`
- `AutoMerge(sourceIds)`：只处理合并规则，不自动改其他布局

### 失败原因

`OutOfBounds`、`Overlap`、`StorageFull`、`InstanceMissing`、`InstanceAlreadyPlaced`、`WouldOrphanPurchase`、`InvalidStateRevision`。

错误位置保持原状态，不自动挤压。自动挤压看似贴心，实则替玩家做了空间决策。

## 4. 法门数据结构

```text
ItemDefinition
- id, displayName, size, basePrice
- tags[]
- baseCooldownTicks
- triggers[]
- effects[]
- contentVersion
- readableSummaryKey

ItemInstance
- instanceId, definitionId
- quality
- refinementId?
- anchorSlot? / storageIndex?
- temporaryModifiers[]
```

### 法门设计模板

每张法门必须填：

| 字段 | 问题 |
|---|---|
| Purpose | 它在什么构筑问题里提供新解法？ |
| Decision | 玩家放它时舍弃什么？ |
| Trigger | 玩家能否在战前预测触发？ |
| Output | 它改变伤害、护体、节奏、蓄力还是失衡？ |
| Dependency | 需要位置、标签、状态还是敌方结构？ |
| Counterplay | 哪类道影使它表现下降？ |
| Failure state | 空转、过慢、走火、占位浪费如何被看见？ |
| Tuning levers | cost/reward/duration/cooldown 各由什么假设支撑？ |

禁止只写“强力核心”“高额伤害”这类无法实现也无法测试的形容词。

## 5. 品质与合并

- `[SCOPE]` 普通、改良、定型三档。
- 两张同名同品质自动合并；普通到定型需要 4 个普通副本。
- 合并保留棋盘实例及位置；多个淬炼时由玩家选择保留一个。
- 品质默认只改效果量，不改触发模板，降低学习负担。
- `[CONTRACT]` 当前品质倍率为 1.00 / 1.60 / 2.40，已进入模拟器、行为断言与 approved hash；其正式内容平衡性仍为 `[TO VALIDATE]`，验证重点是“追副本是否压过位置、转向与淬炼”。

### 品质的设计红线

1. 不能因品质提升让原本带代价的淬炼变成无代价。
2. 不能让同名追卡成为所有经济状态下的最佳 sink。
3. 不能通过改冷却偷偷改变整条触发顺序，除非卡面明确并升级规则版本。

## 6. 淬炼

每个实例最多 1 个淬炼；覆盖旧淬炼是不可逆选择，旧淬炼不返还价值。

| 淬炼 | Gain | Sink / 代价 | 制造的新决策 | 核心失败信号 |
|---|---|---|---|---|
| 加急 | `[CONTRACT]` 冷却 -15% | 每次主动使用 +1 失衡 | 速度是否值得累积走火 | 低频卡白拿速度，代价不发生 |
| 延期 | `[CONTRACT]` 冷却 +20%，效果 +30% | 启动变慢，开战效果不增幅 | 单次质量 vs 周期次数 | 长战斗中收益无条件覆盖成本 |
| 复写 | `[CONTRACT]` 首次主动后 50% 追加 | 不触发相邻响应，不二次消费 | 爆发 vs 连锁价值 | 复制复杂链导致隐式二次消费 |
| 可靠 | `[CONTRACT]` 免疫敌方延迟 | 不能获友方加速 | 针对性稳定 vs 自身上限 | 无延迟环境仍是最优 |
| 静音 | `[CONTRACT]` 每次少 +1 失衡 | 伤害/护体量 x0.85 | 稳定性 vs 效率 | 风险卡被完全洗白 |
| 超额 | `[CONTRACT]` 伤害/护体量 x1.35 | 开战 +3 失衡 | 早期强度 vs 走火窗口 | 战斗太短导致账单永不兑现 |

上述当前百分比和代价语义均受 v0.4.1 契约、行为断言与 approved hash 保护；正式内容平衡性仍为 `[TO VALIDATE]`。候选试验带只登记假设，任何落地数值都必须走规则版本、断言与 hash 评审，不能用调数值改掉“复写不触发相邻、可靠拒绝友方加速”等代价结构。

## 7. 三种构筑方向

构筑方向是分析标签，不是职业锁。

### 快速执行

- 决策：频率组件、降失衡与终结组件如何争格。
- 输入：短冷却、加速、累计次数。
- 输出：早启动、平滑压力。
- 弱点：低单次伤害喂护体；加速可被延迟抵消。

### 护体反制

- 决策：防守何时转成进攻，是否容纳大型枢纽。
- 输入：护体获得、护体损失、受干扰、蓄力。
- 输出：延后兑现的反击。
- 弱点：启动慢；面对成熟连锁可能来不及转化。

### 周天连锁

- 决策：链条方向、阈值、双边相邻与大型挤压。
- 输入：相邻使用、蓄力传递、加速。
- 输出：成型后的高系统效率。
- 弱点：中枢被延迟或位置错误时整体降速。

## 8. Edge Cases

- 满盘/满仓：只允许购买会立即合并的法门。
- 合并后尺寸不变，原位置仍需合法。
- 覆盖淬炼前必须二次确认，并展示失去的规则，不展示虚构“战力变化”。
- 同一实例不能同时在棋盘和仓位。
- 空格是策略状态，不提示为“未完成布局”。
- 多格法门旋转不进入首阶段。

## 9. Failure States

- 自动推荐布局压缩探索。
- 卡面必须展开三级详情才能理解主触发。
- 大型法门采用率低，因为其效果没有改变全局节奏。
- 所有获胜构筑趋向满 8 格，空格从不成立。
- 淬炼代价只存在于文字，样本中极少实际触发。

## 10. Acceptance

### 功能

- 所有命令确定性、可撤销到提交前状态，并返回明确失败原因。
- 规范化快照在 PC/移动逻辑层一致。
- 空格、相邻、多格占位与合并覆盖全部单元测试。

### 体验

- 玩家面对同一道影时，至少能提出两种格位成本不同的合法布局。
- 玩家能预测一项淬炼的收益窗口和账单窗口。
- 代表样本中不存在仅因单位格效率而垄断所有方向的尺寸。
