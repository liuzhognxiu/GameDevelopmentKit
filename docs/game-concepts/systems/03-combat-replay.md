# 03｜确定性战斗、回放与战后复盘系统

## 1. 系统卡

| 字段 | 定义 |
|---|---|
| Purpose | 把战前构筑假设变成可观察、可追溯的结果 |
| Player experience goal | “我看见哪条链成功、哪条链断了，以及为什么” |
| Authority | `buqi-battle-contract.md` v0.4.1 |
| Inputs | 两份规范化 BuildSnapshot、规则/内容版本 |
| Outputs | BattleResult、完整 BattleLog、hash、复盘事实 |
| 边界 | 战中无玩家操作；回放只消费日志，不参与结算 |

## 2. 战斗阶段

`PreTick → Declare → Resolve → Chain → Aggregate → PostTick` 为 `[CONTRACT]`。0.1 秒 tick、整数运算、同 tick 对称结算、蓄力即时声明顺序均不得由表现层改写。

### 玩家可理解版本

| 技术阶段 | 玩家看到什么 | 必须回答的问题 |
|---|---|---|
| 冷却推进 | 法门逐渐接近发动 | 谁会先启动？ |
| 声明 | 法门亮起并锁定关系 | 哪张法门准备做什么？ |
| 连锁 | 相邻路径依次高亮 | 这次响应从哪里来？ |
| 汇总 | 护体、伤害、失衡结算 | 本次交换谁赚了？ |
| 结束检查 | 气血/劫火/胜负 | 为什么现在结束？ |

## 3. 六类效果的反馈通道

| 效果 | 视觉 | 音频 | UI 数值 | 战报 |
|---|---|---|---|---|
| 伤害 | 来源到目标的短路径；气血变化 | 清晰命中，不按每点播放 | 实际伤害与被护体吸收分开 | source、target、actual、absorbed |
| 护体 | 护体层生成/破损 | 生成与碎裂两种音色 | 当前值、溢出值 | granted、effective、overflow |
| 加速 | 冷却环推进节奏标识，不加快动画 | 一次提示，不循环尖叫 | 幅度与剩余时间 | source、coverage |
| 延迟 | 冷却环受阻标识 | 低频阻滞提示 | 幅度、免疫 | source、coverage、immune |
| 蓄力 | 实例上的离散计数 | 获得/消费短促反馈 | 当前值；消费为负变化 | read、consume、snapshot |
| 失衡 | 阈值刻度与临界提示 | 临界前预告、走火单次反馈 | 当前值与阈值 | source、accident、direct damage |

反馈强度服务因果，不服务烟花预算。一次连锁里最重要的来源最亮，所有节点同亮等于都没亮。

## 4. 回放控制

- 暂停、1x、2x、4x、跳过、重播。
- `[PLACEHOLDER]` 默认播放速度 1x；是否允许自动切 2x 必须测试。
- 倍速只改变表现时钟，不改变 tick、日志或结果。
- 表现落后时允许压缩次要动画、追赶时间线；禁止跳过关键因果标记。
- 跳过后直接展示由日志重建的最终状态。

### 关键事件优先级

1. 致胜/致败事件。
2. 核心法门首次发动或未发动。
3. 连锁中断、无合法目标、免疫。
4. 失衡临界与走火。
5. 普通重复触发。

移动端同屏高亮链深 `[PLACEHOLDER]` 最多 3 层；更深链条折叠为“+N 次响应”，点击后展开。验证指标是归因正确率，不是屏幕上能塞多少线。

## 5. 战前预测

预测记录不是玩家属性，也不影响战斗。P-1 使用主持人记录，正式 UI 可以提供可选结构化模板：

```text
我预计：[法门/链条]
会在：[启动/中段/劫火前]
导致：[先造成压力/维持护体/打断核心/走火]
```

系统不能自动替玩家选择预测。否则我们测到的是摘要生成器，不是玩家理解。

## 6. 战后复盘三层信息

### Layer 1：一句结果

- 胜负、结束时刻、双方剩余气血。
- 与战前预测对照：符合 / 部分符合 / 不符合，由玩家确认。

### Layer 2：三条事实

1. 最大有效贡献（伤害或护体）。
2. 最关键连锁/中断。
3. 最大风险账单（失衡、空转、延迟）。

### Layer 3：可审计日志

按 tick、chainId、来源、目标、效果与 reasonCode 查询。面向进阶玩家和开发，不要求首玩逐条阅读。

## 7. 主因生成规则

事实摘要只能引用日志，不做策略推理。合法模板示例：

- “`{item}` 被延迟 `{duration}`，主动使用 `{actual}` 次；对手同类核心使用 `{opponent}` 次。”
- “`{chain}` 在 `{item}` 处因 `{reason}` 中断，共损失 `{missedTriggers}` 次预计响应。”
- “本场发生 `{count}` 次走火，造成 `{damage}` 直接伤害。”

禁止文本：

- “你应该购买 X。”
- “这套构筑太弱。”
- “建议改进摆位。”

系统提供证据，玩家负责订正。

## 8. Edge Cases

| 情况 | 处理 |
|---|---|
| 同 tick 多来源致死 | 展示“同刻结算”，不伪造先手 |
| 双方同时归零 | 明确平局来源 |
| 链条超过表现容量 | 折叠次要响应，日志保持完整 |
| 无合法目标 | 卡面短暂标记空转，复盘列为损失 |
| LoopCapReached | 视为规则/内容异常，强提示并进入 QA |
| 60 秒硬上限 | 展示比较顺序，不能只写“超时失败” |
| A-03 复写 | 标识为回响，不画成第二次主动使用 |
| 蓄力同 tick 消费 | 按声明顺序显示，避免 UI 同时显示两次消费同一蓄力 |

## 9. Failure States 与诊断顺序

1. 玩家主因错误：先查来源/目标高亮与信息层级。
2. 只有降速才看懂：查事件密度、重复动画和链条折叠。
3. 战报正确但玩家不改：查准备系统是否提供针对性 action。
4. 玩家不看战斗只看结算：查战前是否能形成预测、关键窗口是否有张力。
5. 日志与动画不一致：判表现 bug，不调机制。

## 11. Acceptance

### 功能

- 任何播放速度与跳过路径的最终 UI 状态一致。
- 日志可重建全部战斗资源和临时状态。
- PC/目标移动设备使用同一 BattleResult 与 hash。

### 体验

- 玩家能在不读原始日志时指出一个由事实支持的主要原因。
- 玩家能把主因映射到购买、淬炼或摆位中的至少一种行动。
- 1x 是可读速度；若多数玩家必须 0.5x，停止扩内容。
