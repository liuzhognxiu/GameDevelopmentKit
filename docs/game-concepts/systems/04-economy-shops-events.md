# 04｜经济、商店、事件与补偿系统

## 1. 系统卡

| 字段 | 定义 |
|---|---|
| Purpose | 用有限金币把“知道败因”转化为“愿意支付哪种修正成本” |
| Player experience goal | 玩家在准备阶段能说出“这次花费是为了解决上一战哪个事实” |
| Owner | `BuqiRunController` + `EconomyCommandService` + 版本化 `RunState.economy` |
| Inputs | RunState、轮次、准备入口候选、ShopDefinition、EventDefinition、BoardState、RunRandomState |
| Outputs | 金币变化、持有装备变化、临时修正/债务、锁定货架、事件选择结果、StateDelta |
| 核心边界 | 经济只改变准备阶段资源和构筑输入；不得给战斗或对手快照添加隐藏倍率 |

当前文档描述完整首阶段经济责任，但不等于当前可玩范围。P-1 通过前，内部效果验证库和必要调试入口可以继续用于规则/配置回归；不得制作正式商店 UI、完整经济循环，或把验证库整体启用为玩家内容。

## 2. 玩家决策

| 决策 | 玩家问题 | 必须可见的信息 | 禁止答案 |
|---|---|---|---|
| 买入 vs 保留 | 现在补一格，还是攒金币等更合适的装备？ | 当前金币、价格、尺寸、标签、可放置性 | 用“战力上升”替玩家判断 |
| 刷新 vs 锁定 | 是继续找解法，还是保留当前机会？ | 刷新费用、锁定内容、剩余准备次数 | 重开界面重抽 |
| 升级 vs 新购 | 强化已成型关系，还是增加新关系？ | 基础价格、品质、合并规则、位置影响 | 品质永远优于转向 |
| 改造 vs 稳定 | 接受账单换窗口，还是保持可控？ | 收益、代价、代价触发时机 | 代价只写在文本里不发生 |
| 事件安全项 vs 风险项 | 拿确定收益，还是承担下一战风险？ | 选项结果、临时状态持续边界 | 事后才显示真实代价 |
| 出售/移除 | 放弃哪条路径来腾资源？ | 返还值、失去的实例/改造 | 自动清理“低价值”装备 |

经济选择必须能回接 03 的复盘事实：伤害不足、护盾被吃空、核心被延迟、连锁断开、过载伤害或空转。

## 3. 资源与账本

### 3.1 金币 Sources / Sinks

| 项 | 规则状态 | 说明 |
|---|---|---|
| 开局金币 6 | `[PLACEHOLDER]` | 来自 gameplay spec；仍需 P-1/迷你局验证是否形成真实首轮取舍 |
| 每轮基础 +5 | `[PLACEHOLDER]` | 用于保证每轮至少有一次修正机会，数值不作为已验证经济曲线 |
| 胜利额外 +2 / 失败额外 +3 | `[PLACEHOLDER]` | 失败补偿公开显示，不暗改对手或商店概率 |
| 金币上限 20 | `[PLACEHOLDER]` | 防止无限囤积绕过准备取舍 |
| S/M/L 基础价 2/4/6 | `[PLACEHOLDER]` | 绑定尺寸成本假设；不能用调价抹平尺寸取舍 |

经济账本必须记录 `reasonCode`：`RoundGrant`、`WinBonus`、`LossCompensation`、`Purchase`、`Refresh`、`Sell`、`Upgrade`、`Refine`、`EventReward`、`EventCost`、`DrawCompensation`。

### 3.2 临时状态

- 临时过载债务只带入下一场战斗，结算后清除。
- 事件产生的下一战临时加速、护盾或费用折扣必须存为版本化 `TemporaryModifier`。
- 未确认事件奖励、锁定货架和免费刷新次数属于 RunState，不能只存在 UI。
- 任何临时效果进入 `BattleRequest` 前都必须显式出现在双方快照或请求上下文中；战斗日志应能追溯来源。

## 4. 主流程

### 4.1 当前门禁流程

```text
战斗沙盒
-> 使用固定双方快照
-> 不生成商店/事件
-> 可用主持人记录“如果能买/改造，你会改什么”
-> P-1 判断是否进入配置化准备
```

P-1 前允许设计命令、Schema 和测试夹具；不允许把 3 类商店、6 事件或完整经济 UI 当作已批准实现目标。

### 4.2 准备入口生成

1. `RoundStart` 幂等发放本轮基础金币。
2. 根据内容启用阶段读取准备入口池。
3. 使用 `RunRandomState.preparationCursor` 确定性固化两个入口。
4. 固化结果写入 RunState；查看、关闭、恢复不消耗 RNG。
5. 若候选池不足以避免重复入口，返回明确 `InsufficientOfferPool`，不临时补假内容。

### 4.3 商店

1. 进入商店时读取或生成 `ShopState`。
2. 第一次刷新免费；后续刷新费用按规格 `[PLACEHOLDER]` 1、2、2、3、之后 3。
3. 展示 4 个商品、价格、尺寸、标签、品质、是否能放入棋盘/仓位/合并。
4. `Purchase` 成功后立刻写入持有物、金币与合并结果。
5. `LockShop` 只保留商品和价格，不保留免费刷新次数。
6. 离开商店不会自动确认未购买商品。

P-1 固定 9 装备 / 3 改造题目不启用正式商店，只能通过调试快照或测试命令构造输入；24/6/16 内部验证库也不因配置存在而获得经济内容启用许可。

### 4.4 事件

1. 进入事件时固化事件 ID 与可见选项。
2. 读取构筑的 C 选项只在条件满足时显示；不满足时隐藏，不自动替玩家选择 A/B。
3. 所有选项结果在确认前完整显示，包括临时债务、移除、折扣或随机奖励候选。
4. 需要随机展示的奖励先固化候选，再等待玩家确认。
5. 确认后写入 `EventResolved`，重复确认不再次发放。

### 4.5 升级与改造服务

- 升级服务只能提升持有装备一阶，不能提升定型装备；每局次数上限仍为 `[PLACEHOLDER]`。
- P-1 固定题目只向参与者暴露高速、抗减速、复制三种；内部效果验证库已覆盖六种规则语义，但完整服务仍属于后续玩家流程预算。
- 覆盖旧改造必须展示被覆盖规则，确认后不可拆卸、不返还。

## 5. 非法与中断恢复

| 情况 | 处理 |
|---|---|
| 金币不足 | 命令失败，返回 `InsufficientSpiritStone`，状态不变 |
| 棋盘和仓位均满 | 只允许购买会立即合并的同名同品质装备，否则 `NoStorageOrBoardSpace` |
| 购买后合并触发改造冲突 | 暂存 `PendingMergeChoice`，玩家选择保留一个；中断恢复仍停在该选择 |
| 刷新时金币不足 | 保留当前货架，不消耗 RNG |
| 锁定后再次进入商店 | 读取锁定货架；不恢复免费刷新次数 |
| 事件确认前退出 | 保留事件与候选；恢复后不重新抽取 |
| 事件确认后崩溃 | 根据 `eventResolutionId` 幂等恢复，不重复发奖励 |
| 升级/改造目标不存在 | 命令失败并定位目标 ID |
| 内容版本不匹配 | 拒绝恢复该经济选择，要求迁移或归档旧局 |

所有失败返回 `CommandResult`，UI 不先播放扣款或奖励动画。

## 6. Edge Cases

- 出售一个会导致构筑为空的装备：若处于 `BoardReview` 前允许，但 `ConfirmBoard` 必须拒绝无合法快照。
- 负金币不进入首阶段；风险以临时过载债务表达，不以欠款系统表达。
- 事件奖励若会使仓位溢出，必须先让玩家选择放弃、替换或取消；不能自动丢弃。
- 随机奖励确认前必须显示完整候选，不使用“确认后再抽”。
- 失败补偿与平局补偿都要公开写入账本，避免玩家以为系统暗箱调难度。
- 同一轮两个准备入口不能因为 UI 排序变化而交换 RNG 消耗顺序。

## 7. Failure States

- 玩家只追最高价格或最高品质，经济没有制造构筑取舍。
- 失败补偿让故意失败成为最优刷钱路线。
- 商店刷新比阅读战报更能解决问题，玩家进入“摇货架”而非订正构筑。
- 事件文本有趣但结果无法映射到战斗事实。
- 改造代价在代表样本中很少实际发生。
- 经济 UI 建成后，P-1 仍无法证明玩家会根据败因改变购买、改造或摆位。

## 8. 停止线

1. P-1 未完成前，不制作正式商店/事件 UI，不启用完整经济内容，也不把内部效果验证库整体接入玩家候选池。
2. 若玩家在沙盒复盘后不能提出一个经济向改动及预期结果，先改战报和卡面信息，不扩商店。
3. 若 `RunRandomState` 恢复后货架、事件候选或后续随机结果不一致，停止所有经济内容扩展。
4. 若失败补偿被证明优于正常争胜，冻结补偿调参并先重跑经济模拟。
5. 若任一改造在样本中贡献提升超过规格复查线且代价未实际发生，停止新增改造组合。

## 9. 配置边界

| 阶段 | 可启用经济内容 | 不可越界 |
|---|---|---|
| 战斗沙盒 | 0 商店、0 事件；固定快照与 3 验证改造 | 正式购买流程、完整经济 UI |
| 最小配置链路 | 仍为 0 商店、0 事件；可验证经济字段持久化 | 用空 Schema 偷跑完整内容 |
| 三轮迷你局 | 3 商店、3 事件、12 装备、6 改造、9 对手快照 | 未证明闭环前录入剩余 6 装备和后 3 事件 |
| 完整首阶段 | 18 装备、6 改造、3 商店、6 事件、12 对手快照 | 服务器经济、永久货币、赛季、账户成长 |

表中后续阶段只是玩家流程预算，不是当前实现许可。内部效果验证库虽已达到 `24 装备 / 6 改造 / 16 对手快照`，经济许可仍是 0 商店、0 事件；玩家可见启用数量必须由阶段门禁控制。所有价格、刷新费用、奖励和上限若未通过玩家样本验证，保留 `[PLACEHOLDER]` 标签。

## 10. Acceptance

### 功能测试

- 相同 RunSeed、内容版本和操作序列下，准备入口、货架、事件候选和经济账本完全一致。
- 任意界面重开、详情查看和取消确认不消耗 RNG。
- 所有经济命令在金币、仓位、合并、版本错误下返回明确失败原因且状态不变。
- 购买、出售、升级、改造、事件确认和结算奖励均可幂等恢复。
- 临时过载债务进入下一战快照或请求上下文，并在战后清除。

### 体验验证

- P-1 中主持人记录：玩家看完复盘后能否提出一个购买/改造/保留金币的具体计划。
- 三轮迷你局先记录每次战败后的针对性改动，不用 9 轮小样本裁 70%；玩法规格中的 `70%` 作为后续较大正式样本 `[PLACEHOLDER]` 目标。
- 玩家能解释至少一次“没有买”的价值，例如保留金币、避免过载或等待尺寸合适的装备。
- 若多数玩家只说“买更贵的”，判经济表达失败。
