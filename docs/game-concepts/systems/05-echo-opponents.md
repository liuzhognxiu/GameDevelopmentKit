# 05｜道影、对手档案与公平性系统

## 1. 系统卡

| 字段 | 定义 |
|---|---|
| Purpose | 把另一套具体周天变成可读取、可验证、可订正的题目 |
| Player experience goal | 玩家开战前知道主要威胁，战后能判断自己的改动是否针对了这份道影 |
| Owner | `EchoSelectionService` + `EchoArchive` + 版本化 `BuildSnapshot` 校验 |
| Inputs | RunState、daoSeal、player BuildSnapshot、RunRandomState.echoCursor、EchoDefinition、内容/规则版本 |
| Outputs | selectedEchoId、公开情报、对手 BuildSnapshot、fallbackReason、道影选择审计记录 |
| 核心边界 | 道影是同规则构筑快照，不是按玩家进度变强的数值墙 |

历史 Step 3 最小链路为 9 法门、3 淬炼与 6 份离线道影；当前内部效果验证库已扩为 8 构筑方向、24 法门、6 淬炼与 16 份离线道影。P-1 仍只启用固定题目承载认知走查；体验门禁通过前，不得把完整验证库包装成正式异步对手池、在线匹配或正式道影 UI。

## 2. 玩家决策

| 决策 | 玩家问题 | 道影必须提供 | 禁止做法 |
|---|---|---|---|
| 读取威胁 | 这份道影靠什么赢？ | 方向、三张关键法门、主要威胁、占用、已知淬炼 | 隐藏倍率决定强度 |
| 战前预测 | 我的周天能否赶在它成型前解决问题？ | 可支持预测的冷却/关系信息 | 直接给胜率预测 |
| 准备修正 | 我该针对威胁买、淬炼还是摆位？ | 明确的结构弱点或压力来源 | 道影动态克制玩家货架 |
| 战后订正 | 我输给它的哪条链？ | 可与 BattleLog 对齐的 echo itemId/hash | 用模糊标签替代证据 |
| 平局重赛 | 是同题重做还是换同标签题？ | 平局原因、替换规则 | 平局暗扣资源或重抽准备 |

道影的职责是出题。系统可以解释事实，不能替玩家解题。

## 3. Inputs / Outputs / Owner

```text
EchoDefinition
- echoId
- contentVersion
- ruleVersion
- stageGate
- archetypeId
- daoSealRange
- buildInvestment
- boardOccupancy
- keyItemIds[3]
- publicThreatSummaryKey
- snapshotHash
- BuildSnapshot
```

`EchoSelectionService` 只读取合法、启用且版本兼容的定义。它不读取 UI 状态、系统时间、联网状态或玩家最近失败原因来临时改造道影。

### 输出契约

```text
EchoSelectionResult {
  selectedEchoId;
  publicIntel;
  opponentSnapshotHash;
  fallbackReason;
  echoCursorBefore;
  echoCursorAfter;
}
```

`publicIntel` 是战前信息白名单，不包含完整行动日志预测、不包含隐藏评分、不包含未公开淬炼细节。

## 4. 道影制作边界

### 4.1 当前门禁

| 阶段 | 道影来源 | 可验证内容 |
|---|---|---|
| 战斗沙盒 | 代码内测试快照 | 9 法门、3 淬炼、三方向基础交互、日志归因 |
| 最小配置链路 | 6 份离线道影 | 版本化加载、公开情报、兜底选择 |
| 内部效果验证库 | 16 份离线道影 | 8 构筑方向、24 法门与扩展效果的配置/模拟回归；不自动进入玩家候选池 |
| 三轮迷你局 | 9 份离线道影 | 轮次匹配、平局替换、针对性重构 |
| 完整首阶段 | 12 份离线道影 | 教学/前期/成型/混合覆盖 |

P-1 通过前，不制作在线上传、玩家幽灵库、人格标签、赛季池或大规模生成道影。

### 4.2 制作规则

- 每份道影必须是一份合法 `BuildSnapshot`，通过 v0.4.1 校验。
- 道影和玩家使用相同法门、品质、淬炼、临时效果和战斗规则。
- `buildInvestment` 只用于匹配，不显示为战力，不预测联动强度。
- 教学档案展示单一明显联动；前期档案验证第一次升级；成型档案展示核心大型法门；混合档案防止方向标签变答案。
- 旧版本道影无迁移规则时整份拒绝，不静默替换法门。

## 5. 主流程

```text
RoundStart
-> 读取当前 stageGate 下启用的 EchoDefinition
-> 过滤版本、daoSealRange、合法快照
-> 按道印、占用差、投入差匹配
-> 使用 echoCursor 确定性选择
-> 固化 selectedEchoId 与 publicIntel
-> BoardReview 生成玩家快照
-> 创建 BattleRequest
-> 战后保留 echo hash 与日志关联
```

### 5.1 匹配

匹配优先级沿用 gameplay spec：

1. 当前道印范围。
2. 棋盘占用差 `<= 2`。
3. 构筑投入差 `<= 25%`。
4. 使用 `RunSeed + RoundIndex` / `echoCursor` 确定性选择。
5. 无匹配时逐级放宽投入差，最终使用同道印范围兜底档案。

上述数值来自玩法规格，仍需在体验样本中确认是否让道影像“题目”而不是“墙”。

### 5.2 公开情报

战前预览只显示：

- 构筑方向。
- 三张关键法门。
- 主要威胁。
- 棋盘占用。
- 已知淬炼。

不显示完整日志预测、不显示隐藏评分、不显示“推荐购买”。如果 P-1 中玩家无法形成预测，优先调整这五类信息的文案和层级，不增加泄密字段。

### 5.3 平局与换影

- 平局不授道印、不扣道基。
- 立即更换同标签道影重赛，不重新准备。
- 连续第二次平局后，按运行规格给出 `[PLACEHOLDER]` 补偿并进入下一轮。
- 若当前阶段没有可替换同标签道影，返回 `NoAlternateEcho`，使用显式兜底规则；不得隐式重用同一份并伪装成新对手。

## 6. 非法与中断恢复

| 情况 | 处理 |
|---|---|
| 道影含未知法门/淬炼 | 拒绝该道影，记录 `InvalidEchoContent` |
| 规则版本不匹配 | 有迁移规则才迁移；否则拒绝并选兜底 |
| 快照越界/重叠/空构筑 | 不进入战斗，记录 `InvalidEchoSnapshot` |
| 无匹配道影 | 逐级放宽后仍无结果则使用固定兜底；兜底也缺失时阻止开战 |
| 预览后退出 | 恢复同一 selectedEchoId 与 publicIntel，不重新消耗 echoCursor |
| 战斗后崩溃 | 根据 BattleResult 中 echo hash 恢复，不重新选择对手 |
| 平局重赛中断 | 恢复待战道影与平局计数，不重新准备 |
| 内容热更新 | 旧局只在显式迁移成功后继续，否则归档旧局 |

道影选择失败不能退化为“生成一个强度相近的数值敌人”。

## 7. Edge Cases

- 玩家和道影快照完全相同：允许，左右镜像测试必须仍然成立。
- 道影有临时状态：必须显式来自档案定义或事件来源，不能由匹配器临时添加。
- 多份候选排序相同：按稳定 `echoId` 排序后再抽取。
- 公开情报中的三张关键法门若因迁移缺失，整份道影不可用。
- 战后道影不因胜负被修改；异步档案是历史快照，不是学习中的敌方 AI。
- 失衡债务、淬炼和品质都必须进入 snapshot hash，避免 UI 与战斗看到不同对手。

## 8. Failure States

- 玩家感觉道影“突然变强”，但找不到具体法门或连锁原因。
- 公开情报太少，玩家只能开战后才知道题目。
- 公开情报太多，玩家只照着系统给出的答案摆位。
- 道影池按玩家失败原因动态克制，破坏公平感。
- 某一份教学道影因数值过硬变成墙，而不是可识别题目。
- 平衡统计用重复同一确定性对局刷样本量。

## 9. 停止线

1. 任一非法或旧版本道影进入战斗，停止扩充道影池，先修校验。
2. P-1 中玩家无法在开战前说出一个具体威胁，停止录入更多道影，先改公开情报。
3. 战后玩家主因错误主要来自道影预览误导，停止调整经济和战斗数值，先修预览。
4. 道影选择若依赖系统时间、集合迭代顺序或 UI 打开次数，停止所有随机相关实现。
5. 在三轮迷你局前，不启用超过 9 份道影或完整 12 份离线池。
6. 不实现实时 PvP、服务端上传、排行榜、赛季池或反作弊。

## 10. 配置边界

| 配置项 | 当前允许 | 边界 |
|---|---|---|
| `EchoDefinition` | 可定义字段与测试夹具 | 未到阶段不得启用完整 12 份 |
| `BuildSnapshot` | 必须可校验、可 hash | 不允许引用 Unity 场景对象或 UI 状态 |
| `publicThreatSummaryKey` | 可本地化文案 | 不写策略建议 |
| `stageGate` | 控制启用数量 | 不用隐藏开关偷跑后续内容 |
| `buildInvestment` | 用公式计算 | 不显示为战力，不作为胜率承诺 |
| `archetypeId` | fast、buffer、chain、heal、poison、burn、freeze、overload | 当前内部验证库的 8 值分类，不是硬克制或职业标签 |

完整首阶段的 12 份玩家道影是体验预算，不等于内部验证库的物理行数。当前 16 份道影可以参与配置、合法性和模拟回归，但玩家流程只允许 stageGate 明确启用的固定题目；扩大玩家可见池仍需对应阶段门禁。

历史 P-1 题目可在展示层归纳为快速、护体、连锁、混合等较粗认知标签，但持久化快照的 `archetypeId` 必须保留上述 8 值内部分类；展示标签不得反向改写配置枚举或确定性 hash。

## 11. Acceptance

### 功能测试

- 同一 RunSeed、道印、玩家操作序列选择相同道影，并保存相同 echoCursor。
- 打开/关闭预览不改变 selectedEchoId、publicIntel 或 echoCursor。
- 所有道影快照通过 v0.4.1 规范化校验并产生稳定 hash。
- 未知内容、旧版本、越界、重叠和空构筑全部拒绝并确定性兜底。
- 平局换影不重新准备；连续第二次平局的补偿幂等。
- 道影进入 BattleRequest 后，战斗结果只由双方快照和 battle contract 决定。

### 体验验证

- P-1 玩家在战前能用公开情报说出一个具体威胁或预测。
- 战后玩家能把败因指向道影的某张关键法门、链条或节奏窗口。
- 玩家下一轮针对同类威胁改变购买、淬炼或摆位，而不是只要求更高数值。
- 教学道影应让玩家感到“我看懂了题”，不是“系统给了答案”。
