# 06｜UX、首玩教学与跨平台交互系统

## 1. 系统卡

| 字段 | 定义 |
|---|---|
| Purpose | 让玩家在不增加战中操作的前提下，完成“预测—验证—订正”的第一条认知链 |
| Player experience goal | 首玩玩家能独立购买/摆放/开战，并能说出一个下一轮改动理由 |
| Owner | `BuqiUXFlow` + UI 表现层 + `RunCommand` 适配层 |
| Inputs | RunState、BoardState、Echo publicIntel、BattleLog、CommandResult、平台输入事件 |
| Outputs | 玩家命令、预测记录、主因选择、改动意图、可读 UI 状态、体验埋点 |
| 核心边界 | UI 只提交命令和展示日志事实；不能重算战斗、暗改经济或替玩家优化布局 |

当前工程已完成 Step 1/2/3 与 24 装备、6 改造、16 对手快照的内部效果验证库；P-1 仍使用固定 9 装备 / 3 改造题目，且只完成自动构筑玩家 3/3 轮。体验门禁通过前，只允许最小占位界面、主持人记录或调试表单，不制作正式 UI、完整场景、完整经济界面或长期 onboarding。

## 2. 玩家决策路径

| 阶段 | 玩家需要做的事 | UX 必须帮助理解 | UX 不该做 |
|---|---|---|---|
| 起始方案 | 选择想先学习的关系 | 三套方案分别教什么关系 | 标“推荐最强” |
| 对手快照预览 | 读出主要威胁 | 方向、关键装备、占用、已知改造 | 给胜率或购买建议 |
| 棋盘整理 | 放置、收回、交换、确认 | 尺寸、相邻、空格阻断、非法原因 | 自动挤压或自动摆位 |
| 战前预测 | 写/说一个可证伪判断 | 装备、窗口、预期结果模板 | 系统代填预测 |
| 战斗回放 | 看见链条如何运转 | 来源、目标、冷却、护盾、过载、空转 | 倍速改变结果 |
| 战后复盘 | 指认主因 | 三条日志事实和证据跳转 | 先给策略建议 |
| 下一轮准备 | 做一次针对性改动 | 把主因映射到购买/改造/摆位入口 | 用新手引导强迫固定答案 |

首玩教学只教“如何形成判断”，不教“哪套构筑最强”。

## 3. Inputs / Outputs / Owner

### 3.1 UI 输入

- `RunState.phase` 决定当前允许操作。
- `BoardState` 提供 8 格占位、仓位、实例与非法原因。
- `Echo publicIntel` 提供战前情报白名单。
- `BattleLog` 提供回放与复盘事实。
- `CommandResult` 是 UI 状态变化的唯一依据。

### 3.2 UI 输出

```text
UXOutput
- RunCommand
- PredictionRecord
- CauseRecord
- ChangeIntent
- ViewTelemetry
- AccessibilityState
```

`ViewTelemetry` 只记录体验诊断需要的行为：查看情报、移动次数、非法尝试、预测是否具体、跳过回放、主因选择、下一轮改动类型。它不作为战斗或商店输入。

## 4. 主流程

### 4.1 P-1 占位流程

```text
主持人/调试界面展示双方 8 格快照
-> 玩家说出预测
-> 运行战斗沙盒
-> 查看 Layer 1/2 复盘事实
-> 玩家说出主因
-> 玩家说出下一轮会改什么
```

该流程用于验证认知，不验收正式交互、美术或完整经济。若 P-1 失败，不能用“做正式 UI 后会更好”跳过问题。

### 4.2 首玩正式流程的最小骨架

1. `StarterSelection`：三套起始方案并列，展示关系而非强度。
2. `EchoIntel`：用对手快照预览建立题目。
3. `PreparationA/B`：进入商店、事件、升级或改造；当前门禁前不启用正式版本。
4. `BoardReview`：以命令结果展示合法/非法状态。
5. `PreBattlePrediction`：一个主预测，可跳过但要记录。
6. `Battle`：日志驱动回放，支持暂停、倍速和跳过。
7. `Summary`：一句结果、三条事实、可审计日志入口。
8. `ChangeIntent`：玩家选择或填写下一轮想改的方向。

## 5. 跨平台交互原则

### 5.1 命令等价

同一操作必须同时存在鼠标/键盘与触摸路径：

| 操作 | PC 路径 | 触摸路径 | 等价命令 |
|---|---|---|---|
| 查看装备 | 悬停/点击 | 轻点 | `InspectItem` |
| 放置 | 拖拽或选择目标格 | 拖拽或点选装备再点格位 | `Place/Move` |
| 交换 | 拖到另一装备 | 点选两张装备 | `Swap` |
| 收回 | 拖到仓位/按钮 | 长按或操作菜单 | `ReturnToStorage` |
| 确认棋盘 | 按钮/快捷键 | 固定确认按钮 | `ConfirmBoard` |
| 回放控制 | 空格/按钮/快捷键 | 固定控制条 | `Pause/Speed/Skip` |

如果某平台只能通过精细拖拽完成关键操作，则判交互不可交付。点选式替代路径不是辅助功能，而是主路径之一。

### 5.2 信息层级

- 8 格棋盘、双方生命值/护盾/过载、当前关键触发是战斗第一层。
- 装备详情、完整数值和日志查询是第二层或抽屉。
- 原始 BattleEvent 表是第三层，服务进阶玩家和 QA。
- 移动端不能把关键因果塞进悬停 tooltip；所有悬停信息必须可点击打开。
- 长名称、数值和 reasonCode 不得相互遮挡；看不清是 UX bug，不是玩家问题。

### 5.3 表现与模拟分离

- 倍速、暂停、跳过和动画追赶只改变表现时钟。
- UI 从 BattleLog 重建状态，不调用战斗计算分支。
- 动画落后时可以折叠次要响应，但不能省略致胜、核心中断、过载伤害或无目标。
- 任何平台帧率、区域设置、字体回退都不能改变命令结果或日志 hash。

## 6. 非法与中断恢复

| 情况 | 处理 |
|---|---|
| 拖拽取消 | 回到原位置，不发送半命令 |
| 非法放置 | 显示具体原因：越界、重叠、仓位满、实例缺失；状态不变 |
| 双击/连点确认 | 根据 stateRevision 幂等处理，只确认一次 |
| 回放中切后台 | 保存播放位置；恢复后仍读取同一 BattleResult |
| 跳过回放 | 展示由日志重建的最终状态和复盘事实 |
| 屏幕旋转/窗口缩放 | 保留阶段、选中项和未确认选择，不重新生成候选 |
| 低性能导致动画落后 | 追赶或折叠表现，不改变日志顺序 |
| 输入法/语言切换 | 不影响预测、主因和日志字段的结构化值 |

UI 异常恢复不得重新抽商店、事件或对手快照。

## 7. Edge Cases

- 玩家跳过预测：允许继续，但记录 `PredictionSkipped`，P-1 不把该轮计入“形成预测”成功样本。
- 玩家只看复盘不看战斗：可接受一次，但若成为主路径，需要调整战斗高亮。
- 小屏幕无法同时展示完整棋盘和详情：优先保留棋盘与当前操作反馈，详情进抽屉。
- 多层连锁超过显示容量：折叠为 `+N 次响应`，点击展开；日志保持完整。
- 没有鼠标悬停的平台：所有解释都必须有点击路径。
- 文案本地化变长：布局按内容自适应，不截断关键数值和原因。
- Debug/P-1 界面不得遗留为正式 UX 标准；它只证明认知链。

## 8. Failure States

- 玩家能按按钮完成流程，但不知道自己为什么赢或输。
- 教学箭头让玩家复现固定答案，而不是理解取舍。
- 棋盘自动整理让玩家错过尺寸和相邻的真实成本。
- 移动端误触导致玩家不信任构筑编辑。
- 回放特效盖过因果，玩家只等结算摘要。
- 正式 UI 早于 P-1 建成，掩盖卡面、对手快照情报或战报本身的问题。

## 9. 停止线

1. P-1 通过前，不制作正式 UI、完整商店/事件界面、完整 onboarding 或复杂演出。
2. 若玩家无法在无正式 UI 的沙盒中形成“预测—结果—主因—改动”，先修信息与规则表达。
3. 若 UI 显示状态与 BattleLog 不一致，停止体验调优，先修日志消费。
4. 若触摸路径无法稳定完成放置、交换、收回和确认，停止扩展移动端内容。
5. 若长文本或按钮在目标分辨率发生遮挡，停止新增界面文案。
6. 若多数玩家必须读原始日志才能归因，先重做 Layer 1/2，不扩内容。

## 10. 配置边界

| 配置项 | 允许 | 不允许 |
|---|---|---|
| TutorialStep | 记录阶段、目标命令、文案 key | 写死推荐构筑答案 |
| CardSummary | 展示尺寸、触发、收益、代价 | 隐藏代价到高级详情 |
| EchoIntelView | 展示公开情报白名单 | 泄露完整模拟预测 |
| ReplayPriority | 控制高亮/折叠优先级 | 改变 BattleLog 或结果 |
| InputBinding | 映射到相同 RunCommand | 平台专属规则分支 |
| TelemetryKey | 记录体验诊断 | 作为经济、对手快照或战斗输入 |

P-1 阶段可用表格、调试面板或主持人记录替代正式配置。正式 UI 文案与控件只有在认知链成立后才进入制作。

## 11. Acceptance

### 功能测试

- 同一 UI 操作在鼠标、键盘和触摸替代路径下产生相同 `RunCommand`。
- 非法布局不改变 BoardState，并展示明确失败原因。
- 回放暂停、倍速、跳过、重播后的最终 UI 状态一致。
- UI 关闭重开、窗口缩放、屏幕旋转不改变 RNG 游标、对手快照、货架或事件候选。
- 1280x720、1920x1080、2560x1440 与目标移动纵/横屏下，关键文本和数值不互相遮挡；若目标移动规格未锁定，标 `[PLACEHOLDER]` 并在 P-1 后补。
- BattleLog hash 与 UI 展示来源一致；表现层无战斗计算入口。

### 体验验证

- P-1 玩家在主持人最小辅助下完成一次预测、观看、归因和下一轮改动陈述。
- 正式首玩沿用 gameplay spec：无讲解首玩能独立完成购买、摆放和开战。
- P-1 的 9 轮只裁决三类参与者能否形成具体预测、证据归因与针对性改动，不用百分比制造虚假精度。
- 后续正式首玩样本目标：`[PLACEHOLDER]` 80% 的战斗后能指出日志支持的主因；`[PLACEHOLDER]` 70% 的战败后能做针对性改动。
- 玩家能说出至少一个尺寸、相邻、冷却或改造代价带来的取舍。
- PC 与移动端的失败原因差异若主要来自操作误触或阅读困难，先修 UX，不调战斗数值。
