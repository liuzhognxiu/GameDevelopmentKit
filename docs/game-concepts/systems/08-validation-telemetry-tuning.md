### 3.2 每轮固定协议

1. 展示双方 8 格快照与当前公开道影情报。
2. 不解释策略，让玩家提交一句战前预测。
3. 固化预测后运行真实 Battle Sandbox。
4. 展示 Layer 1/2 通俗摘要；需要时允许查日志。
5. 让玩家先说主因，再展示设计者解释。
6. 提供购买、淬炼、摆位三个成本明确的改动选项。
7. 玩家选择一项并写预期结果。
8. 下一轮只改变该项，其他输入和 seed 按测试题设计固定。

### 3.4 剩余 6 轮执行与交接

1. 在已通过编译和 `Game.Hot.Buqi.Tests` 的主 Unity 工程中打开 `Game/Buqi/Battle Sandbox`。
2. 保持默认的“P-1 固定三轮模式”，自走棋玩家选择 `AutoChessPlayer`，新手选择 `NewPlayer`；同一参与者连续完成三轮并使用稳定的匿名 ID。
3. 每轮先填写可证伪预测并锁定，再运行战斗。结果曝光前可以取消本次预测；结果曝光后不能清空或重开，必须完成本轮。结果绑定时会独立保存最小曝光墓碑；若主会话缺失/损坏，或 domain reload 后当前模拟器无法复现原 hash，则失败关闭且原参与者不能重试。替代流程会先创建并持久化不同参与者的锁定批次，成功后才删除旧墓碑。允许跳过，但该轮不能成为 Gate 评审候选，不能事后补写预测。
4. 先阅读 Layer 1/2 摘要，再按需查看原始日志；把支持主因判断的 `BattleEvent.Sequence` 填入证据事件 ID。
5. 填写主因、`Purchase | Refinement | Position` 中的一项主要改动、预期影响和可选主持人备注，然后完成本轮。
6. 只有窗口显示“可交给独立评审”时才导出 JSON；导出记录的 `EligibleForGateReview` 必须为 `true`，且 `BatchId`、`AttemptId`、`RoundIndex`、`QuestionId`、`BattleLogHash`、`EvidenceEventIds` 和规则/模拟/内容版本可回查。该字段只表示结构完整，不自动计入 Gate。
7. 成功导出后“开始下一轮”才解锁；同一批次保持参与者 ID/画像，并强制按三道固定题目的唯一顺序推进。每类画像必须得到同批次的 3 份结构合格 JSON；跳过、非固定题目或无证据记录只能作为诊断材料。
8. 六份真人记录齐备后，由未主持本次走查的人逐条判断证据是否支持主因、样本是否有效，再独立汇总失败信号和分布并给出“通过 / 不通过 / 样本不足”。在此之前状态保持“样本不足”，不得实现正式 Step 4 UI。

建议把原始 JSON 保存到未跟踪的 `output/buqi-p1/<batch-id>/`，只把脱敏汇总结论纳入版本库。自动化测试、智能体代答和设计者自行填写都不能替代这六轮真人样本。

## 4. 失败信号与处理顺序

| Code | 坏掉长什么样 | 优先诊断 | 处理 |
|---|---|---|---|
| A 无预测 | 只能说“试试看” | 卡面、道影公开量 | 减少并重排信息，不先调胜率 |
| B 错归因 | 主因与日志证据不一致 | 回放反馈、摘要层级 | 先修来源/目标/中断表达 |
| C 无重构 | 知道原因但选项无法处理 | 准备选项与成本 | 重画购买/淬炼/摆位选项 |
| D 唯一解 | 多人只因净数值选择同一项 | 机会成本、公开量 | 增加真实账单或保留不确定性 |
| E 伪变化 | 改动与预期无因果关系 | 记录模板、玩家理解 | 收紧针对性定义 |
| F 账单不发生 | 风险描述存在但样本不兑现 | 战斗时长、触发频率 | 调账单窗口，不先加更大惩罚 |
| G 操作污染 | 移动端误触/阅读导致失败 | UX | 不调战斗数值 |

诊断顺序：**输入信息 → 反馈通道 → 可用行动 → 数值平衡 → 内容量**。倒序处理通常会得到更多卡，以及同一个问题。

## 5. Gate 裁决

### 通过所需证据

- 三类参与者各完成 3 轮。
- 多数轮次存在具体、可证伪的战前预测。
- 主因有 BattleLog 证据，而非只复述胜负。
- 下一轮改动针对主因，且玩家能说明预期结果。
- 同一测试题不存在稳定净数值唯一解。
- 自动测试、hash 与玩家看到的摘要一致。

“多数”暂不写百分比；完成首批 9 轮后，根据实际分布设正式门槛并版本化。样本只有 9 轮时写 80.00%，通常是在给小数点安排角色扮演。

### 未通过后的动作

- A/B：回到卡面、道影情报或复盘，不进入 Step 4。
- C/D/E：重画三类改动题，再跑同一类参与者。
- F：调整已标 `[PLACEHOLDER]` 的 cooldown/reward/duration，保留行为语义。
- G：补触摸等价路径并复测，不改规则核。

## 6. 埋点模型

### 6.1 认知链

```text

- participantType, scenarioId, roundIndex
- subjectItemOrChain
- expectedWindow
- expectedOutcome
- skipped

CauseRecord
- causeCode
- sourceItemIds[]
- evidenceEventIds[]
- confidence

- type: Purchase | Refinement | Position

```

### 6.2 行为与经济

记录：准备入口、货架展示、刷新、锁定、买卖、升级、淬炼、事件选项、每次棋盘变化、非法命令原因、轮末灵石、未消费原因。

### 6.3 战斗

记录：快照 hash、结果、时长、主要结论形成时刻、贡献、护体有效量、延迟覆盖、蓄力生成/消费、走火、空转、LoopCapReached、暂停/倍速/跳过。

首阶段不收集聊天、社交关系或与核心验证无关的数据。

## 7. 观察与解释分离

| Observation | Interpretation | 下一实验 |
|---|---|---|
| 玩家 3 次查看冷却详情 | 可能缺少一层摘要，也可能在认真计算 | 对比显示首次触发时间的版本 |
| 玩家输后买高品质卡 | 可能追数值，也可能正确处理伤害不足 | 询问并记录预期变化，检查主因 |
| 玩家跳过战斗看摘要 | 战斗反馈可能冗长，也可能已知结果 | 比较关键事件压缩版本 |
| 灵石常到上限 | sink 不够或选择都无价值 | 记录未花原因，不直接提高价格 |

Playtest 记录先写发生了什么，再写设计解释。把解释写进观察栏，数据就提前学会站队了。

## 8. 经济模型

### 8.1 Sources / Sinks

```text
Sources = 开局 + 轮次收入 + 胜负补偿 + 事件 + 出售 + 平局补偿
Sinks   = 购买 + 刷新 + 升级 + 淬炼 + 事件成本
NetFlow(round) = Sources(round) - Sinks(round)
```

每条模拟路径至少包含：保守囤积、持续刷新、追同名升级、频繁转向、连续失败、连续胜利。

### 8.2 Monte Carlo 输入

- RunSeed 与四条独立随机流。
- 玩家策略 policy，不用“完全随机玩家”代替目标用户。
- `[PLACEHOLDER]` 初始/每轮/胜负资源与价格。
- 内容阶段 gate。

### 8.3 输出与风险

- 轮末灵石分布与达到上限比例。
- 每轮可承担的有效修正次数。
- 因资源不足无法处理明确败因的比例。
- 故意失败路线的期望收益。
- 刷新成本占总 sink 比例。
- 同名追卡与转向策略的机会成本。

停止线：故意失败的期望长期价值高于正常争胜；或多数玩家常驻上限而没有有意义 sink。

## 9. 战斗与构筑平衡

### 样本规则

- 使用不同合法构筑交叉对战并交换左右阵营。
- 重复相同确定性对局只验证 hash，不增加胜率样本量。
- 按投入档和方向等权汇总。
- 固定生成器 10,000 构筑用于异常、循环和性能，不混入方向胜率。

### 复查指标

| 指标 | 当前门槛 | 状态 |
|---|---:|---|
| 方向代表样本胜率 | 40%–60% | `[PLACEHOLDER]` 首轮目标 |
| 单法门获胜构筑采用率 | >75% 复查 | `[PLACEHOLDER]` |
| 淬炼贡献提升且代价未发生 | >50% 复查 | `[PLACEHOLDER]` |
| 平衡样本 LoopCapReached | 0 | `[QUALITY]`；任何合法样本触发都先按规则/内容异常处理 |
| 压力样本 LoopCapReached | <0.01% | `[PLACEHOLDER]` |

这些数值是报警阈值，不是自动 nerf 指令。先查样本、投入和账单是否真实发生。

## 12. 总停止线

1. P-1 未通过，不进入正式 Step 4 UI。
2. 玩家不能在 1x 下理解核心链，不扩内容。
3. 购买主要只追品质，不扩完整经济。
4. 任一方向长期超过代表样本警戒线，冻结内容扩充。
5. 合法构筑稳定触发事件上限，回到规则/内容原语。
6. 单局中位超过 `[PLACEHOLDER]` 15 分钟，重画流程而非只加跳过。
7. 新效果超出 `buqi-effects-cv1` 且没有独立契约、内容版本和跨端测试，停止扩容。
8. 自动测试失败时不启动玩家测试；玩家测试失败时不以自动测试通过作为放行理由。
