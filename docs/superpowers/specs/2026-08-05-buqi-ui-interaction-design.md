# 《不器》UI 与交互方案

- 日期：2026-08-05
- 状态：设计稿待用户审阅；实现仍受 P-1 门禁阻断
- 范围：当前 P-1 低成本认知走查 + Step 4 之后正式 UI 蓝图

## 1. 决策摘要

采用“P-1 单根走查壳 + 正式 Run Shell”的混合方案。

- 当前只允许 Editor/调试用途的 P-1 走查壳，不创建正式 UIForm、prefab、商店、事件、经济循环或 onboarding。
- P-1 走查壳验证“预测 -> 观看 -> 归因 -> 针对性改动”是否成立，不验证美术完成度。
- P-1 通过后，正式客户端以 GameHot `StarForceUIForm` 为入口，用一个 Run Shell 承载单局阶段，阶段内容由静态 Widget 切换。
- UI 只读取版本化状态、提交 `RunCommand`、展示 `CommandResult` 和重放 `BattleLog`；不直接修改 `RunState`，不重算战斗，不消费 RNG。
- PC、鼠标/键盘、手柄与触摸最终映射到同一命令；拖拽始终有点选式替代路径。
- 视觉使用“不器”的水墨、机关、残器与修仙包装，但信息层级优先于氛围。

当前真实门禁是 P-1 进行中：自动构筑参与者完成 3/3 轮，总进度 3/9；自走棋玩家与新玩家各剩 3 轮。正式 Step 4 UI 不得提前实现。

## 2. 方案取舍

### 方案 A：立即制作完整多窗体 UI

每个阶段使用独立 UIForm，先把主菜单、商店、棋盘、战斗和结算做完整。优点是页面边界直观；缺点是会在 P-1 前投入大量 prefab、配置和交互成本，并可能用表现掩盖卡面、公开情报和战报本身的问题。拒绝。

### 方案 B：只保留现有日志和菜单摘要

继续用 Console/摘要文本完成全部 P-1。优点是成本最低；缺点是无法稳定记录结构化预测、证据选择与下一步改动，也无法验证信息层级。只作为故障兜底，不作为目标方案。

### 方案 C：P-1 走查壳 + 正式 Run Shell

P-1 使用单窗口、固定题目和真实 BattleResult；通过后再把同一认知链迁移到正式 Run Shell。它把当前验证成本控制在最小范围，又提前锁定正式 UI 的状态、命令、组件和导航边界。采用。

## 3. 体验目标与成功条件

玩家不是“把按钮按完”，而是完成一条可审计认知链：

```text
看懂公开题目
-> 提交一个可证伪预测
-> 观看真实日志驱动的战斗
-> 指认一个有证据的主因
-> 提出一个只改主要变量的下一步
```

成功条件：

1. 玩家在开战前能指出具体法门、时间窗口或关系，而不是只说“试试看”。
2. 玩家在不读原始事件表的情况下，能从三条以内事实中指出主要原因。
3. 玩家选择的主因能追溯到真实 `eventId`、`chainId` 或结果字段。
4. 下一轮改动能说明目标、预期效果，并尽量只改变一个主要变量。
5. 暂停、倍速、跳过、窗口缩放、屏幕旋转和界面重开都不改变结果、候选或 RNG 游标。

## 4. 阶段门禁

| 阶段 | 可以做 | 不可以做 | 放行条件 |
|---|---|---|---|
| 当前 P-1 | Editor 走查壳、固定 9/3 题目、结构化记录、真实回放/摘要 | 正式 UIForm、prefab、经济、事件、完整 onboarding、验证库整体启用 | 三类参与者各 3 轮完成并形成明确 Gate 结论 |
| Step 4A | Run Shell、棋盘编辑、道影情报、预测、回放、复盘 | 完整商店/事件和复杂演出 | 认知链在正式输入路径仍成立 |
| Step 4B | 最小准备入口、购买/淬炼、轮次结算 | 扩内容、长期成长、联网道影 | 命令、保存恢复和经济账本门禁通过 |
| 首阶段完善 | 完整首阶段页面、叙事短切片、无障碍与性能打磨 | 排行、赛季、实时 PvP、永久数值成长 | 功能、体验、性能和跨端验收通过 |

内部 `8 构筑/24 法门/6 淬炼/16 道影` 是配置与模拟验证库，不是玩家可见内容预算。

## 5. 顶层信息架构

```text
启动/资源检查
-> 主菜单
   -> 继续单局
   -> 新开单局
      -> 起始方案
      -> 轮次题目/道影情报
      -> 准备选择 A
      -> 准备选择 B
      -> 周天盘确认
      -> 战前预测
      -> 战斗回放
      -> 复盘归因
      -> 改动意图
      -> 轮次结算
      -> 下一轮 / 单局终局
```

### 5.1 启动与主菜单

- 资源初始化前只使用 Builtin 进度/错误能力；普通业务 UI 不抢跑资源系统。
- 主菜单第一视觉信号是“不器”标题与回环巷实景，不做营销式功能介绍。
- 主要命令只有继续、新局、设置、退出。存在可恢复单局时“继续”获得主焦点。
- 放弃单局必须展示当前道印、道基、轮次和不可逆后果，再提交一次明确命令。

### 5.2 单局阶段

- 起始方案展示关系、尺寸和节奏，不显示战力分或“推荐”。
- 道影情报只显示公开白名单：方向、关键法门、主要关系、投入档、一个已知风险。
- 准备入口读取已固化候选；打开、关闭、预览不会重抽。
- 周天盘是每轮主要工作面，8 格连续关系始终可见。
- 预测在确认棋盘后提交；系统不自动填写答案。
- 战斗阶段无战斗命令，只有表现时钟控制。
- 复盘先一句结果，再三条事实，最后才允许展开原始日志。
- 轮次结算幂等；重复点击或崩溃恢复不重复发放。

## 6. 导航与窗体架构

### 6.1 当前 P-1

使用一个 Editor 走查窗口，不进入 `UI.xlsx`，不生成 `UIFormId`，不创建资源 prefab。窗口包含固定五步：题目、预测、运行、归因、改动。它直接调用现有 Battle Sandbox/摘要能力并保存结构化记录。

### 6.2 正式 GameHot 路径

正式阶段统一走 GameHot，不同时建设 ETUI 版本。联网或 ET 场景真正成为需求后，再设计桥接层。

| UIForm | UIGroup | 职责 | 多实例/覆盖 |
|---|---|---|---|
| `BuqiMainMenuForm` | `Default` | 继续、新局、设置入口 | 单实例，暂停被覆盖 |
| `BuqiRunShellForm` | `Default` | 单局状态条、阶段导航与当前阶段 Widget | 单实例，保持单局上下文 |
| `BuqiDetailForm` | `Pop` | 法门、淬炼、道影与证据详情 | 单实例，按 userData 重置 |
| `BuqiConfirmForm` | `Pop` | 不可逆命令确认 | 可复用，但同一命令只保留一个有效确认 |
| `BuqiRawLogForm` | `Pop` | Layer 3 日志筛选 | 单实例，不影响播放位置 |
| `BuqiMessageForm` | `Message` | 非阻塞失败、保存和状态提示 | 短生命周期 |
| `BuqiGuideForm` | `Guide` | P-1 通过后的首玩聚焦遮罩 | 单实例，绝不自动执行命令 |

`RuntimeInspector` 只用于调试，不承载玩家功能。新 UIGroup 不是当前方案的一部分。

### 6.3 Run Shell Widget

`BuqiRunShellForm` 同时只打开一个主阶段 Widget：

- `StarterSelectionWidget`
- `EchoIntelWidget`
- `PreparationChoiceWidget`
- `ShopWidget`
- `EventWidget`
- `RefinementWidget`
- `BoardEditorWidget`
- `PredictionWidget`
- `BattleReplayWidget`
- `BattleSummaryWidget`
- `RoundSettlementWidget`
- `RunTerminalWidget`

阶段切换来自 `RunState.phase + stateRevision`，不是按钮自行隐藏/显示后假定流程已经推进。详情、确认和原始日志使用 Pop 层，不把主阶段 Widget 叠成卡片套卡片。

## 7. 版式系统

### 7.1 PC

最低验证尺寸为 1280x720，主验证尺寸为 1920x1080 和 2560x1440。

- 顶部：道印、道基、轮次、灵石与当前阶段，固定高度，不因数值变化位移。
- 左侧：阶段轨迹与当前题目，只显示已到达阶段，不做可任意跳转的导航。
- 中央：周天盘、商店、事件或战斗的主要工作面。
- 右侧：上下文详情/公开情报/事实证据抽屉，同一时刻只承担一种职责。
- 底部：当前可提交命令与合法性反馈；确认按钮不随错误文本上下跳动。

### 7.2 移动横屏

- 中央保留完整 8 格一行周天盘，顶部状态压缩为图标加数值。
- 详情使用右侧抽屉；抽屉打开时仍保留棋盘至少 60% 宽度。
- 战斗控制条置于底部安全区，暂停、速度、跳过具有稳定触控尺寸。

### 7.3 移动竖屏

最低验证逻辑尺寸为 360x800。8 格仍保持单行连续关系，不拆成 4x2；每格使用图标、尺寸轮廓和状态标记，详细文本进入底部抽屉。

- 顶部：紧凑状态条。
- 中部：8 格盘与当前选择的关系高亮。
- 下部：仓位/候选的横向列表和主命令。
- 底部抽屉：法门详情、合法性原因、公开情报或复盘证据。
- 旋转时保留选中实例、未确认预测草稿、播放位置和 stateRevision。

任何断点都不能让按钮、长名称、数值、reasonCode 或前后内容互相遮挡。固定格式控件使用明确的最小/最大尺寸和 aspect ratio，不按视口宽度缩放字体。

## 8. 核心交互

### 8.1 周天盘

鼠标/触摸拖拽与“点选来源 -> 点选目标格 -> 确认”并存；键盘/手柄使用焦点移动、拾取、放置。

- 合法预览只高亮将占用的连续格。
- 越界、重叠、仓位满和实例缺失显示不同原因，失败后保持原状态。
- 交换、收回、覆盖淬炼和确认棋盘分别提交独立命令。
- 空格是策略状态，不显示为错误或“未完成”。
- UI 不自动挤位置、不自动整理、不根据“推荐强度”改盘。

### 8.2 战前预测

结构固定为三个字段：

```text
对象：法门或关系
窗口：启动 / 中段 / 劫火前
预期：先压低气血 / 维持护体 / 打断核心 / 引发走火
```

允许跳过，但记录 `PredictionSkipped`，该轮不计入 P-1 的预测成功样本。提交后锁定；战斗结果不能回写或改写预测。

### 8.3 战斗回放

- 播放控制为暂停、1x、2x、4x、跳过和重播。
- 倍速只改变表现时钟；跳过后用同一 BattleResult/Log 重建终态。
- 第一层始终显示双方 8 格、气血、护体、失衡/过载、当前关键触发。
- 关键高亮优先级：致胜/致败、核心首次发动或未发动、连锁中断/免疫/无目标、走火、普通重复触发。
- 多层连锁显示前三层，其余折叠为 `+N 次响应`；展开只影响表现。
- A-03 复写标为回响，不伪装成第二次主动使用；同 tick 事件明确“同刻结算”。

### 8.4 复盘与改动意图

Layer 1：胜负、结束 tick、双方剩余气血/护体，以及玩家自己选择的“符合/部分符合/不符合”。

Layer 2：最多三条日志事实：最大有效贡献、关键连锁/中断、最大风险账单。每条事实可跳到对应事件或时间段。

Layer 3：按 tick、chainId、来源、目标、效果和 reasonCode 筛选的原始日志。

主因由玩家从事实中选择，并绑定 evidence event IDs。UI 不写“你应该买 X”“这套太弱”或预测胜率。下一步只记录命令类型、目标与预期效果。

## 9. P-1 走查壳

### 9.1 输入

- 固定题目 ID 与参与者画像。
- 左右双方合法 BuildSnapshot 与公开情报。
- 已锁定的 PredictionRecord。
- 真实 BattleResult、BattleLogHash 和日志事实。
- CauseRecord 与 ChangeIntent。

### 9.2 五步流程

1. **题目**：显示双方 8 格快照、公开威胁和本轮唯一变量。
2. **预测**：主持人或玩家录入对象、窗口、预期；锁定后不可编辑。
3. **运行**：调用现有沙盒，显示结果 hash、关键 tick 和最小回放控制。
4. **归因**：先显示 Layer 1/2，让玩家选择主因并关联证据。
5. **改动**：记录下一轮唯一主要改动与预期；导出完整轮次记录。

### 9.3 P-1 禁止项

- 不显示自动策略建议、推荐卡、战力、胜率或隐藏对手评分。
- 不制作正式坊市、事件、淬炼服务或奖励动画。
- 不把 24/6/16 验证库整体开放为候选。
- 不把走查壳的密度、样式或操作方式当成正式 UX 验收结果。

### 10.1 直接复用的公共组件

| `CommonToggleWidget` | 日志筛选、reduce-motion 与二元设置 |

### 10.2 P-1 通过后新增的领域 Widget

| Widget | 单一职责 | 关键状态 |

| `BuqiEchoIntelWidget` | 公开情报白名单 | collapsed/expanded/version-error |
| `BuqiPredictionWidget` | 结构化预测与锁定 | draft/locked/skipped |

## 11. 视觉与反馈

- 主材质：浅宣纸、墨黑、旧铜与深木；青玉用于有效/治疗，朱砂用于危险/失衡，寒青用于冰冻，金色仅用于道印和关键确认。
- 不用单一棕色覆盖所有层级；资源、危险、控制、治疗和选中必须可由形状、图标和文本同时区分。
- 周天盘、坊市货架、篆刻淬炼台和道影剪影保留实体隐喻，但点击区域与状态反馈遵循统一组件规则。
- 卡面第一层只显示名称、尺寸、主触发、主收益和代价标记；完整数值进入详情。
- 关键命令反馈 120-180ms；回放动作由 tick 时间线驱动。reduce-motion 下取消位移、抖动、闪白和墨迹扩散，用透明度、描边和静态状态替代。
- 音频只确认命令结果和关键战斗事实；失败提示不用高频连续音，不以音频作为唯一状态通道。

## 12. 输入、无障碍与本地化

- 触摸目标最小 44x44 逻辑像素；相邻危险命令保留间距。
- 所有 hover 信息都有点击/焦点路径；移动端不依赖 tooltip。
- 焦点顺序按状态条 -> 主工作面 -> 详情 -> 主命令，弹层打开后焦点被限制在弹层内，关闭后回到触发控件。
- 键盘/手柄与触摸提交同一 `RunCommand`；输入提示来自绑定系统，不写死平台按键。
- 颜色不是唯一语义；冻结、毒、灼烧、过载、非法和选中都有独立图标/轮廓。
- 关键文本对比度至少 4.5:1；装饰文字不承载数值、原因或命令。
- 文案容器按中英文长文本预留换行，不用省略号截断关键原因；原始 reasonCode 只在 Layer 3 显示。
- 动画、粒子、屏幕震动和高对比闪烁均受独立设置控制。

## 13. 状态、命令与数据流

```text
RunState / BoardState / Echo publicIntel
  -> immutable PhaseViewModel(stateRevision)
  -> UIForm / Widget render
  -> user intent
  -> RunCommand(expectedRevision)
  -> CommandResult(success/failureReason/stateDelta)
  -> new immutable ViewModel
```

```text
BattleResult + BattleLog + approved hash
  -> ReplayProjector
  -> presentation frames / Layer 1-3 facts
  -> UI render
```

不变量：

1. UI 不直接写 `RunState`、BoardState、货架、道影或 RNG cursor。
2. 成功动画只在成功 `CommandResult` 后播放。
3. 重复确认由 command ID、settlement ID 和 stateRevision 幂等处理。
4. ReplayProjector 只能消费日志，不能调用 `BuqiBattleSimulator.Simulate`。
5. 摘要只能引用日志/结果字段，不生成策略判断。
6. ViewTelemetry 是诊断输出，不能成为战斗、经济或匹配输入。

## 14. 生命周期与所有权

- `OnInit` 只缓存一次性引用；`OnOpen` 校验 userData、建立本次 ViewModel 和回调；`OnClose` 结束可用周期并取消异步任务。
- Run Shell 是阶段 Widget、事件订阅、临时资源和异步请求的唯一顶层 Owner。
- Pop Form 拥有自己的详情/确认异步请求；关闭后迟到结果必须丢弃。
- 静态 Widget 由最近 Form/父 Widget 初始化，宿主在每次 `OnOpen` 显式 `OpenUIWidget`。
- CodeBind 只生成绑定 partial；业务命令、默认值和错误处理写在非生成文件。
- UI 配置只改正确模式的 `UI.xlsx`，由 Luban 生成 ID 与配置；生成文件禁止手改。
- GameHot 业务逻辑位于 HybridCLR 热更 `Game/Hot/Code/UI`；稳定基类和公共组件边界保持在现有基础层。
- 动态 Widget 当前存在 prefab asset 卸载责任缺口；正式方案优先静态 Widget。必须动态加载时先定义实例销毁、asset 卸载、取消和迟到结果策略。

## 15. 加载、空态、错误与恢复

| 情况 | UI 行为 | 状态原则 |
|---|---|---|
| RunState 加载中 | 保留壳与阶段占位，显示 Loading | 不接受业务命令 |
| 无可恢复单局 | 隐藏继续，主焦点转到新局 | 不构造假存档 |
| 版本不兼容 | 显示版本、原因和归档/返回路径 | 不换卡、不重抽 |
| 命令 revision 过期 | 刷新 ViewModel，保留可安全恢复的草稿 | 不本地回滚伪状态 |
| 非法放置 | 原布局不变，定位格位和原因 | 不自动修正 |
| 资源/Widget 加载失败 | 关闭 loading，显示重试/返回 | 重试不重复命令 |
| 战斗回放中断 | 保存播放位置并恢复同一结果 | 不重新模拟 |
| 摘要证据缺失 | 标记数据异常并开放原始日志 | 不编造主因 |
| 跳过回放 | 投影到同一终态和摘要 | hash 不变 |
| 旋转/缩放/后台恢复 | 重建布局，保留阶段、选择和草稿 | 候选与 cursor 不变 |
| 连点确认 | 只保留首个有效 command ID | 结算一次 |

错误提示必须描述可执行原因，例如“占用格 7 越界”或“状态已更新，请重新确认”，不只显示“操作失败”。

## 16. 埋点边界

P-1 记录：参与者画像、题目 ID、预测是否具体、预测锁定时间、是否跳过、选择的主因、evidence IDs、下一步改动和主持人备注。

正式 UI 可追加：详情展开、回放控制、非法命令原因、布局命令、准备入口、经济账本与阅读时长。

禁止记录或使用：系统自动生成的策略评分、隐藏胜率、用于动态削弱对手的行为标签，以及把 UI 浏览行为回灌到当前对局规则。

## 17. 验证矩阵

### 17.1 P-1

- 三类参与者各 3 轮，记录完整五步认知链。
- 每轮使用真实 BattleResult/Log/hash，不使用手写胜负结论。
- 预测锁定后不可修改；摘要引用可定位证据。
- 单变量变体仍保持唯一主要改动。
- P-1 失败时先修卡面、公开情报或 Layer 1/2，不进入正式 UI。

### 17.2 正式 UI 功能

- 鼠标拖拽、点选替代、键盘/手柄和触摸产生同一命令。
- 连续打开/关闭两次，验证 userData、回调、Widget、资源和事件没有残留。
- 异步加载期间关闭 Owner，不发生迟到回写或孤立对象。
- 重开、旋转、缩放和恢复不消费 RNG，不改变候选。
- 暂停、倍速、跳过和重播的最终 UI 状态一致。
- BattleLog hash 与 UI 数据源一致，表现层没有模拟入口。

### 17.3 视觉与跨端

- PC 1280x720、1920x1080、2560x1440。
- 移动竖屏 360x800、横屏 800x360，并覆盖安全区缺口。
- 最长中文/英文名称、四位数资源、负数和 reasonCode 不遮挡相邻内容。
- reduce-motion、色觉替代、键盘焦点、手柄焦点和屏幕阅读顺序可用。
- 低性能追赶只折叠次要动画，不丢关键事实。

## 18. 实现拆分边界

本文不是实现计划。P-1 Gate 通过后，按以下顺序分别写计划和评审：

1. **Step 4A-1**：Run Shell、阶段 ViewModel、输入映射和状态恢复。
2. **Step 4A-2**：周天盘、道影情报、预测、回放和三层复盘。
3. **Step 4B**：准备入口、最小经济、事件、淬炼和轮次结算。
4. **Step 4C**：首玩 Guide、叙事短切片、视觉/音频与无障碍打磨。

每个计划都必须先定义 UIForm/Widget Owner、Luban 输入、CodeBind 生成物、命令契约、目标分辨率、异常路径和 Unity 验证证据。任何阶段发现认知链失败、日志与表现不一致、触摸无等价路径或恢复会改变候选，立即停止扩面。

## 19. 设计自检结论

- 无未决占位项；移动验证尺寸和阶段边界已明确。
- P-1 工具与正式 UI 的职责没有混用。
- 正式架构使用现有 UGF 分组、GameHot、StarForceUIForm、Widget 容器、CodeBind、Luban 与 HybridCLR 边界。
- 所有状态改变都有命令来源，所有战斗显示都有日志来源。
- 完整流程已覆盖加载、空态、错误、中断恢复、PC/移动、无障碍和 reduce-motion。
